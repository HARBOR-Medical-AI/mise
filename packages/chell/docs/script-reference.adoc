== Purpose

This document is a complete reference for writing ChELL scripts and automation.
It covers every builtin command, option, and scripting pattern.
An agent reading this document should be able to produce correct `.chell` scripts
without further context.

== Grammar Rules

All resource commands follow `<object> <verb>` order — never `<verb> <object>`.

[cols="1,1"]
|===
| Correct | Wrong

| `feed list`
| `list feed`

| `plugin info pl-dircopy-v2.1.1`
| `info plugin pl-dircopy-v2.1.1`

| `feeds list --all`
| `list feeds --all`

| `proc refresh`
| `refresh proc`

| `proc retry`
| `retry proc`
|===

Filesystem commands are exceptions: `ls`, `cd`, `cat`, `rm`, `cp`, `mv`, `mkdir`,
`touch`, `tree`, `du`, `upload`, `download`, `edit` follow the standard Unix form.

== Execution Modes

[source,bash]
----
# Interactive REPL
chell

# Single command
chell -c "ls /home/alice"

# Multiple commands separated by semicolons
chell -c "cd /home/alice/uploads; ls -l; cat notes.txt"

# Script file (explicit)
chell -f workflow.chell

# Script file (auto-detected by .chell extension)
chell workflow.chell

# Shebang script
#!/usr/bin/env chell
----

=== Script file format

A script and a manifest (`docs/manifest.adoc`) are one format with one runner: `chell -f f` and `chell f` play the file, as `play f` does. It may carry a manifest's `@` header (`@param`, `@answers`), each line is shown as it runs, and the script stops at its first refused line and exits non-zero.

[source,bash]
----
#!/usr/bin/env chell
# Comments start with #
connect alice http://localhost:8000/api/v1/ s3cr3t
cd /home/alice/uploads
ls -l
upload ~/local_data .
----

=== Stop-on-error flag

A script always stops at its first refused line; `-e` is accepted and changes nothing for it. For a `-c` batch, `-e` stops at the first failing command:

[source,bash]
----
chell -e -c "cd /nowhere; ls"   # stops after the cd
----

== Connection

=== connect

[source,bash]
----
connect --user <user> --password <pass> <url>

# Compact form: user@url (password prompted if omitted)
chell chris@localhost:8000/api/v1/
chell -p chris1234 chris@localhost:8000/api/v1/
----

In a `.chell` script the flags form is more readable:

[source,bash]
----
connect --user chris --password chris1234 http://localhost:8000/api/v1/
----

=== logout

[source,bash]
----
logout
----

=== sudo

`sudo` is explicit, command-scoped CUBE elevation—not Unix UID elevation. It
asks the active surface for an administrator username and hidden password, then
uses that CUBE token only while its nested command runs. The normal session and
saved token are unchanged. A surface without secure hidden input fails clearly.

[source,bash]
----
sudo group adduser pacs_users peter.hong
sudo plugin add pl-dircopy
----

Do not rely on an automatic retry after a permission failure: use the copyable
`Try: sudo …` suggestion emitted for known administrator operations.

=== user

`user` manages CUBE-local accounts only. It cannot create, disable, or remove a federated identity. Account creation prompts for email and a hidden password twice; new local accounts are not automatically PACS users.

[source,bash]
----
sudo user add jack.bivowac
sudo user inspect jack.bivowac
sudo user disable jack.bivowac
sudo user enable jack.bivowac
sudo user remove jack.bivowac
----

== System Introspection

=== id

Print the authenticated CUBE user ID, ChELL's projected primary group, and all
CUBE group memberships:

[source,bash]
----
id
# uid=42(alice) gid=42(alice) groups=42(alice),7(pacs),9(research)
----

CUBE has no primary-group field, so the projected GID equals the UID and the
projected group name equals the username, matching `/etc/passwd`. The `groups`
field then includes every CUBE membership, ordered by numeric group ID.

=== whoami

Prints the authenticated CUBE username.

[source,bash]
----
whoami
# rudolphpienaar
----

=== whereami

Prints the current CUBE URL. Use `pwd` for the ChELL working directory.

[source,bash]
----
whereami
# http://localhost:32223/api/v1/
----

== Directory Listing

=== ls

[source,bash]
----
ls [options] [path]

-l          long format (type char, owner, size/status, date, name)
-h          human-readable sizes (use with -l)
-a          show hidden entries
-d          show the directory entry itself, not its contents
--sort <field>    name|size|date|owner  (default: name)
--reverse   reverse sort order
----

Type characters in long format:

[cols="1,3"]
|===
| Char | Meaning

| `d`  | CFS directory
| `-`  | CFS file
| `l`  | `.chrislink` symlink
| `p`  | Plugin (in `/bin`)
| `P`  | Pipeline
| `v`  | VFS entry
| `j`  | Job/instance node (in `/proc/jobs`)
|===

For `j` (job) entries, the size column is replaced by the colour-coded execution
status string: `finishedSuccessfully`, `started`, `scheduled`, `finishedWithError`,
`cancelled`.

[source,bash]
----
ls
ls -l
ls -lh
ls /proc/jobs/feed_1107
ls -l /bin              # list registered plugins
ls /etc                 # list virtual config files
----

=== tree

Recursive listing in ASCII tree form.  Descends into `dir`, `vfs`, and `job` types.

[source,bash]
----
tree [--dirs|--dirpath] [path]
----

`--dirs` retains the ASCII hierarchy but omits files. `--dirpath` emits one
absolute directory path per line and is suitable for copying, filtering, or
selecting a target for `cd`.

[source,bash]
----
tree
tree /proc/jobs/feed_1107   # full DAG of a feed's jobs
tree /home/alice/data
tree --dirs /home/alice/data      # directory hierarchy only
tree --dirpath /home/alice/data   # full directory paths only
----

=== du

Disk usage summary for a directory tree. `-h` and `--human-readable` are size-formatting flags, not help aliases; both retain a following path operand. A recursive scan can be stopped with Ctrl-C. Cancellation is cooperative, so it returns after any current CUBE listing completes.

[source,bash]
----
du [options] [path]
du --human-readable test-upload
du -sh test-upload
----

== File Operations

=== cat

[source,bash]
----
cat [--binary] [--highlight[=language] | --no-highlight] <file> [file...]
----

Binary mode is auto-detected for `.dcm`, `.png`, `.zip`, `.pdf`, etc.
Use `--binary` to force.

Recognized source and configuration files are syntax-highlighted automatically
when output goes directly to an interactive terminal. Use `--highlight` to force
extension/content inference, `--highlight=python` to select a grammar, or
`--no-highlight` for raw text. Normal pipes and redirects remain ANSI-free.

[source,bash]
----
cat readme.txt
cat analysis.py
cat source --highlight=python
cat config.json --no-highlight
cat /etc/compute.yaml
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/status
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/log
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/params
----

=== upload

[source,bash]
----
upload <local_path_or_glob> <chris_path>
----

Recursively uploads a local file or directory tree. The local endpoint also accepts a host-filesystem glob; every match is uploaded with one aggregate progress display. A file goes inside an existing target directory; only an existing nested target of a directory upload requires merge confirmation. In remote mode, the local endpoint remains the daemon host until client-local transfer support is added.

[source,bash]
----
upload ~/data/study .
upload /tmp/results.csv /home/alice/uploads/
upload ~/Pictures/earthandmoon* .
----

=== download

[source,bash]
----
download <chris_path_or_glob> <local_path>
----

Downloads one CFS file or directory to the daemon host. The shell expands an unquoted CFS source glob before dispatch; every match downloads into one host-local destination directory with aggregate progress. The local destination is always literal. Status, errors, and overwrite confirmation are delivered to the issuing surface.

[source,bash]
----
download /home/alice/results/*.nii /tmp/results/
----

=== pull

Alias for download.

[source,bash]
----
pull <chris_path> <local_path>
----

== Virtual Filesystem Paths

ChELL presents a unified path tree mixing CFS (real ChRIS storage) and VFS
(synthesised from API resources).

[cols="1,1,3"]
|===
| Path | Type | Content

| `/home/<user>/`         | CFS | Uploaded files and directories
| `/home/<user>/feeds/`   | CFS | Analysis feeds and their output trees
| `/PIPELINES/`           | CFS | Shared pipeline output data
| `/PUBLIC/`              | CFS | Publicly accessible files
| `/SERVICES/`            | CFS | Service-level data (e.g. PACS)
| `/SHARED/`              | CFS | Cross-user shared data
| `*.chrislink`           | CFS | Symbolic links to other ChRIS paths
| `/bin`                  | VFS | Every registered plugin as a virtual executable
| `/usr/bin`              | VFS | Built-in shell commands (`id`, `whoami`, `whereami`)
| `/etc/`                 | VFS | Config files (see below)
| `/net/pacs/queries/`    | VFS | PACS query result sets
| `/proc/jobs/`          | VFS | Job monitoring DAG (see <<job-monitoring>>)
|===

=== /etc files

[cols="1,3"]
|===
| Path | Content

| `/etc/compute.yaml` | All compute environments in YAML
| `/etc/group`        | POSIX-style group listing with cached CUBE memberships
| `/etc/passwd`       | User listing
| `/etc/cube`         | CUBE instance information
|===

[source,bash]
----
cat /etc/compute.yaml    # inspect available compute environments
cat /etc/group           # list groups and members
cat /etc/passwd          # list users
----

== Plugin Execution

=== Direct invocation (primary form)

Plugins live in `/bin` as virtual executables.  Type the plugin name directly —
ChELL resolves context from CWD automatically.

[source,bash]
----
pl-dircopy-v2.1.1 --dir .
pl-fshack-v1.2.0 --inputFile brain.mgz --outputFile brain.nii
----

Two cases depending on CWD:

==== Case 1: CWD is outside a feed

ChELL creates a new feed automatically:

1. Runs `pl-dircopy` on the current directory to stage data.
2. Attaches your plugin to the dircopy instance.

A pipeline run from `/bin` with no operand does the same: outside a feed, `pl-dircopy` roots a new feed on the current directory and the pipeline runs off that root (the scheduled answer says `newFeed`); inside a feed node, the pipeline runs off that node.

[source,bash]
----
cd /home/alice/uploads/SAG-anon
pl-fshack-v1.2.0 --inputFile brain.mgz --outputFile brain.nii
# → new feed created, pl-fshack scheduled as child of pl-dircopy
----

Use `--` to pass feed-level context separately from plugin params:

[source,bash]
----
pl-fshack-v1.2.0 --inputFile brain.mgz -- feed_title="Brain MRI Study" instance_title="FreeSurfer recon"
----

==== Case 2: CWD is inside a feed

ChELL extracts the `previous_id` from the path and attaches directly.

[source,bash]
----
cd /home/alice/feeds/feed_123/pl-dircopy_456/data
pl-segmentation-v1.0.0 --threshold 0.5
# → attaches to instance 456, no --previous_id needed
----

Works identically from a `/proc/jobs` path:

[source,bash]
----
cd /proc/jobs/feed_123/pl-dircopy_456
pl-segmentation-v1.0.0 --threshold 0.5
----

=== Naming the run

A plugin runs by its name, where the session stands: in a plain folder it makes a feed rooted on that folder; inside a feed node it continues off that node. To run off another node, `cd` to it first. A capture names the run, so later lines say which run they mean:

[source,bash]
----
A=$(pl-dircopy-v2.1.1 --dir .)
cd ${A.outputPath}
expect run ${A.instanceId} status eq finishedSuccessfully
----

The answer is a `run.scheduled` model: `pluginName`, `instanceId`, `feedId`, `newFeed`, `outputPath`, `status`. `set A` shows it whole. See `help variables` and `docs/manifest.adoc`.

== Pipeline Execution

A *pipeline* is a registered template (named, reusable graph of plugins with
wired parameters).  A *workflow* is a live instantiation of a pipeline on a feed.

=== pipeline list

[source,bash]
----
pipeline list [--search <term>] [--all] [--limit <n>]
pipeline inspect <id>
pipeline manifest <name|id|slug>
----

=== workflow create

Instantiates a pipeline as a workflow on an existing feed node.

[source,bash]
----
workflow create <pipeline_id> --previous_id <instance_id>
----

[source,bash]
----
pipeline list
workflow create 7 --previous_id 456
jobs list --feed 123
----

=== Running a pipeline directly (from /bin)

Pipelines registered in `/bin` can be invoked directly.  Flags route to the
appropriate subcommand:

[cols="1,2"]
|===
| Flags | Action

| (none)                        | run the pipeline
| `--nodes` or `--parameters`  | show pipeline info
| `--source` or `--readme`     | show pipeline source
| `--manifest`                 | emit complete registered invocation YAML
| `--paramFile <cfs-file>`     | apply one sparse CFS YAML overlay
| `--<node>.<field> <value>`   | override a hosted parameter or node execution control
|===

[source,bash]
----
my-pipeline --previous 456
my-pipeline --nodes
my-pipeline --manifest
my-pipeline --segmentation.threshold 0.5 --segmentation.memory_limit 8Gi
my-pipeline --paramFile ~/experiments/run-1.yaml
----

`cat /bin/my-pipeline` emits a fast cached executable summary and points to the
explicit inspection command. `pipeline manifest my-pipeline` (or
`my-pipeline --manifest`) emits the complete registered CUBE invocation YAML,
including pipeline and piping IDs. `pipeline source my-pipeline` emits the
original authoring YAML.

=== groups / group

[source,bash]
----
groups list [--all]
group inspect [<group>]
group members <group>
group adduser <group> <user...>    # [admin]
group removeuser <group> <user...> # [admin]
----

Membership changes operate on an existing CUBE user and require an
administrator token. Use an exact group name in ordinary work; numeric CUBE
IDs remain accepted for scripts and as an escape hatch. A name is never
interpreted as a partial search result.

When the ordinary CUBE identity is denied a known administrator operation,
ChELL preserves the CUBE error and prints a copyable `sudo` suggestion. `sudo`
prompts on the active surface for an administrator username and hidden password,
uses the resulting token only for its nested command, then discards it. It does
not replace or persist the normal session identity.

[source,bash]
----
group members pacs_users
sudo group adduser pacs_users peter.hong joe.schmo
group removeuser pacs_users joe.schmo
cat /etc/group
----

Each requested user is reported. Adding an existing member and removing a
non-member are successful no-ops; if another user in the same batch fails,
ChELL still attempts every requested change and returns a non-zero status.

`/etc/group` is a read-only projection of the current users in each visible group. The first read hydrates memberships from CUBE and shows an interactive spinner when that takes longer than 300 ms. The rendered projection is cached for five minutes per CUBE connection; `group adduser` and `group removeuser` invalidate it immediately, while changes made through Django admin become visible after the freshness window. Progress is status telemetry and therefore does not enter pipes, redirects, or captured command output. During startup, each blocking cache step—including this membership hydration—gets up to three complete attempts, with 250 ms then 500 ms backoff. A daemon terminal reports failed attempts as `[RETRY]`; after the final failure it asks whether to continue with degraded caches or exit before publishing its berth. A non-interactive daemon keeps the availability-first behavior and starts degraded rather than hanging.

See link:posix.adoc[posix.adoc] for the record mapping, cache lifecycle, and daemon behavior of POSIX-style projections.

== Job Monitoring: /proc/jobs

`/proc/jobs/` surfaces all visible plugin instances as a navigable DAG.
Each feed is a directory; each plugin instance within it is a subdirectory.

=== Structure

[source]
----
/proc/jobs/
└── feed_1107/
    ├── status          ← aggregate: running|finishedSuccessfully|finishedWithError|…
    ├── title           ← feed name
    └── pl-dircopy_64267/           ← type=job, shown with trailing /
        ├── status      ← live API fetch if non-terminal
        ├── params      ← key=value lines, what the plugin ran with
        ├── log         ← stdout/stderr, always live
        └── pl-shexec_64295/
            ├── status
            ├── params
            ├── log
            └── …
----

=== Common patterns

[source,bash]
----
# List all feeds with aggregate status
ls -l /proc/jobs

# See full DAG of a feed
tree /proc/jobs/feed_1107

# Read live status of a specific node
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/status

# Read log output
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/log

# Read what params a job ran with
cat /proc/jobs/feed_1107/pl-dircopy_64267/pl-shexec_64295/params

# Cancel a running job
rm /proc/jobs/feed_1107/pl-shexec_64295

# Cancel all jobs in a feed
rm -r /proc/jobs/feed_1107
----

=== proc command

[source,bash]
----
proc refresh              # rebuild /proc feed index (fast — feeds only)
proc refresh feed_123     # scope rebuild to one feed
proc refresh 123          # same
proc retry                # resume a failed global topology sweep

proc find <instance_id>   # return full /proc path for any instance ID
proc here                 # navigate from a known output directory to its producing job
----

`proc find` example:

[source,bash]
----
proc find 64306
# → /proc/jobs/feed_1107/pl-dircopy_64267/.../pl-neurofiles-push_64306

# Then read status directly:
cat $(proc find 64306)/status
----

After following a job's `data` link into CFS, use `cd -` for the immediate
return. `proc here` can instead navigate from that output directory (or a
descendant) to its producing `/proc/jobs` node. It works from output paths
resolved in the current session and never guesses a feed or CFS path layout.

=== /proc cache behaviour

* Built lazily on first access to any `/proc/jobs` path.
* `proc refresh` rebuilds the feed index (fast, feeds only).
* `proc retry` retains completed pages and continues at the page that failed.
* Instance nodes within a feed are loaded on first access to that feed's directory.
* Status of non-terminal nodes is always fetched live from the API on `cat status`.
* `/proc` paths bypass listCache — always fresh.

=== Prompt themes

ChELL abbreviates the authenticated user's home directory in the prompt:
`/home/alice` is shown as `~`, and `/home/alice/uploads` as `~/uploads`.

* `prompt default` selects the compact single-line theme.
* `prompt p10k` selects the vivid, two-line Powerlevel10k-inspired theme with
  background-filled powerline segments and high-contrast Font Awesome icons.

Both themes share the same high-contrast truecolor palette. The `p10k` theme
also supports optional PACS, time, duration, and status segments; run
`prompt --configure` to choose them interactively. Its Font Awesome icons and
powerline separators require a Nerd Font.

The p10k segment order is PACS, CUBE URL, user, path, `/proc`, then the optional
physical-mode indicator and command telemetry. During topology loading, `/proc`
uses an orange snowflake for a cold index, a slate refresh icon for cached
reconciliation, and a red warning when refresh fails. The segment disappears
when the index is current.

== Scripting Patterns

=== Wait for a job to finish

`/proc` status is always live for non-terminal jobs.  Poll with a loop:

[source,bash]
----
#!/usr/bin/env chell
# Run a plugin and wait for completion
cd /home/alice/uploads/study
pl-fshack-v1.2.0 --inputFile brain.mgz
# Note the instance ID from the output, then:
# (in a loop externally) cat /proc/jobs/<feed>/pl-fshack_<id>/status
----

=== Continue analysis from a known node

[source,bash]
----
cd /proc/jobs/feed_123/pl-dircopy_456
pl-segmentation-v1.0.0 --threshold 0.5
----

=== Find and inspect a job by ID

[source,bash]
----
proc find 64306

=== Upload data and run analysis

[source,bash]
----
#!/usr/bin/env chell
connect --user alice --password s3cr3t http://cube:8000/api/v1/
cd /home/alice/uploads
mkdir study-2024
cd study-2024
upload ~/local_data/brain.mgz .
pl-fshack-v1.2.0 --inputFile brain.mgz --outputFile brain.nii -- feed_title="Brain recon 2024"
----

=== Check compute environments before running

[source,bash]
----
cat /etc/compute.yaml
store install pl-fshack --compute ares
----

=== Install a plugin with explicit elevation

[source,bash]
----
sudo store install pl-fshack --compute ares,argentum
----

=== List all running jobs

[source,bash]
----
proc refresh
jobs list --search status:started
----

=== Run a pipeline on existing data

[source,bash]
----
pipeline list
# find pipeline ID, e.g. 7
cd /home/alice/feeds/feed_123/pl-dircopy_456/data
workflow create 7 --previous_id 456
jobs list --feed 123
----

== Output Conventions

Commands that succeed produce output on stdout.  Error messages go to stderr.
Exit code is 0 on success, non-zero on failure.

In `-c` or script mode, each command's output is emitted as it runs.
`proc refresh` and `store install` print a status line on completion.

== Tab Completion (interactive only)

* Command names complete from all registered builtins.
* Plugin names (with version suffix) complete from `/bin`.
* Path arguments complete from the VFS using `vfsDispatcher`.
