== Abstract

A Trusted Domain (TD) is built from a *bastion*: one host that runs the mise stack and, beside it, the tools and the keys for one cloud. There are two bastions, and they are the same shape with different contents. The *Hub bastion* is the cloud controller: it sits at the Hub Trusted Domain, outside every tenancy it builds, holds the cloud keys, and lays a spoke Trusted Domain down in three layers, each through its own door. The *spoke bastion* is a runner inside a spoke's own cluster, next to that spoke's cohort: code written at the Hub is shipped to it as source and run there under the spoke's policy, and only `/outgoing` comes back; it holds that TD's CUBE token and nothing else. A third host, the *Hub dev bastion*, is where the developer edits; it holds door tokens for spoke bastions and no cloud key. This document draws the Hub bastion and the spoke bastion, names what runs where, and corrects two lines in <<stratus.adoc#bastion,stratus.adoc>> that placed the bastion inside the tenancy.

The companion documents are <<stratus.adoc#,stratus.adoc>> (the substrate backend the Hub bastion hosts) and <<linux-metaphor.adoc#,linux-metaphor.adoc>> (the machine metaphor every column of the figure is drawn in).

[[figure]]
== The Hub bastion

image::images/bastion-hub.png[The Hub bastion: a person's surfaces on the left, the host with the mise stack in the centre, Red Hat and a spoke Trusted Domain on the right, with three lines from the session to three doors]

The mise stack (centre) presents a POSIX-like machine metaphor from which many backends can be controlled; here a cloud tenancy backend with an OCI driver (right). The user, human or agent (left), interacts with the bastion from a surface such as ARGUS (web) or chell (terminal). POSIX-like abstractions drive, deploy and monitor the creation of a spoke Trusted Domain; the mise layer normalizes backends to a single metaphor. The bastion, itself a VM or a pod, holds the cloud tenancy's own command-line tools beside the mise stack. It never runs inside a tenancy it builds and never holds patient data.

Read column by column.

[[person]]
=== Where the person is

Two surfaces, one session. ARGUS in a browser shows DOMAINS, CAPACITY and STEPS, a view of the tenancy; its console is a chell running on the bastion under a pty (#1125). chell in a terminal runs on a workstation or a tablet with a door token (#925). Both do the same two things in the same order: log in at the door, then attach to the one calypso over the wire. One calypso, many surfaces; nothing on the person's side holds a credential or runs a command.

[[host]]
=== The host

The bastion is a host: a VM today (the operator's workstation, or titan), a container on the Hub cluster once the Hub Trusted Domain is itself an OpenShift cluster. Everything in the centre column is a process on that host, and the lineage is fixed:

* *init starts porter.* systemd on a VM; the container entrypoint in a pod. porter is the door, and the only way in from outside.
* *porter starts calypso*, one per identity, on its berth.
* *calypso spawns a pty per console*: ARGUS's console is a chell on one of them.

The host has no door of its own. There is one path to its shell, and it is drawn in the figure: chell, through porter, to calypso, and `!` under the `tasks` tier opens the host shell. No ssh, no `oc rsh`, no other door is part of the design. A shell appears only when that path opens one, and the tools in it are the cloud's: `terraform`, `oci`, `oc`, `helm`, `dig`. The driver runs those same tools itself through the supervised runner (<<stratus.adoc#tasks,stratus.adoc>>), so a person and a step reach the host the same way and see the same files.

The credential files are on the host and are read by both floors: `~/.oci/config` holds an API key per spoke tenancy, a kubeconfig exists per cluster the bastion built, and the Red Hat token lives under the domain's state. The OCI driver inside calypso and `terraform` in the shell read the same files; nothing is copied out, and no CUBE token and no patient data are anywhere on the host.

[[session]]
=== The session: the same trio as ChRIS

calypso here hosts a stratus session with the `tasks` tier on. brasa supplies the tree and the `domain` verbs; the tenancy is mounted at `/net/oci/<tenancy>/`, and a spoke is a folder under `domains/`. Below brasa the stratus package repeats the ChRIS backend's three roles with other names: the fond providers in `vfs/` play salsa's role, `CloudDriver` and its OCI implementation in `cloud/` play cumin's role, and Oracle's per-service `oci-*` SDK packages play chrisapi's role. "Driver" in this document is that code of ours; the cloud's own API and Terraform stack are the thing it drives.

[[doors]]
=== Three layers, three doors

A spoke Trusted Domain is three layers, and the session reaches each through its own credential. The figure draws them as three lines leaving calypso:

[cols="1,2,3",options="header"]
|===
| Door | Target | What passes through it
| the API key | Oracle Cloud Infrastructure: the API, and the `oci-openshift` Terraform stack | `terraform apply` lays the nodes (three control, three workers), the VCN, subnets, load balancers, volumes and the bucket that holds the discovery ISO. Billing starts here.
| the Red Hat account | Red Hat's Assisted Installer | registers the cluster, issues the discovery ISO the bastion uploads to the bucket, takes the OCI manifests, and installs OpenShift on the nodes as they boot from the ISO and call home. OpenShift lands on the nodes from Red Hat's side, not from Terraform.
| the kubeconfig | the cluster API of the OpenShift just built | `helm` and `oc` deploy ChRIS; afterwards the Kubernetes driver reads the cluster through the same file.
|===

The spoke reads bottom up as a machine: Oracle's API lays the nodes; OpenShift is the cluster on those nodes; ChRIS is the application on that cluster. The spoke never reaches back; the bastion reaches out, through the cloud API before the cluster exists and through its kubeconfig after.

[[posture]]
=== Posture

* The Hub bastion runs *outside* every tenancy it builds. It exists before any spoke and outlives every one. A Hub bastion that is a pod on the Hub cluster is still outside each spoke: the Hub cluster is not a spoke.
* It holds cloud keys and no cluster-management role. The RHACM hub, when it comes (<<stratus.adoc#fleet,stratus.adoc>>), sits beside it on the Hub cluster, holds cluster management and no cloud key, and spoke agents pull from it.
* There is no scheduler in the picture. A schedule, if one is wanted, is `chell -c` under cron on the host: a shell line, not a component.
* There is no instance principal. The bastion never runs inside a tenancy, so its identity is the key file, as <<stratus.adoc#identity,stratus.adoc>> describes.

[[spoke]]
== The spoke bastion: code comes to the cohort

image::images/bastion-spoke.png[The spoke bastion. Top row: the developer at the Hub, the Hub dev bastion where code is written, the spoke bastion where it runs. Below: the logical view, a project directory over a cohort with the policy on its two mounts, and /outgoing returning to the developer]

The spoke bastion has nothing to do with the cloud, little to do with the cluster, and only one thing to do with ChRIS: ChRIS gathered the cohort and ChRIS receives the results. It is a coding surface over a cohort: a host with a shell, a project directory, and two mounted directories. It is not a plugin and runs nothing as one. <<dev-bastion.adoc#,dev-bastion.adoc>> is its own document: the problem, the mechanism, and the reasons behind the policy; this section is the summary.

[[spoke-logical]]
=== The logical view

* *The cohort* is identified and collected by ChRIS before any code arrives: a feed, a `gather`, one TD's data.
* *The project directory* is where code lands: `~/project/` with scaffolding pre-built, `incoming/` holding the cohort, `outgoing/` for results, `src/` for the code, and `run`. Code runs as an ordinary process in the shell; the two directories are its whole data surface.
* *Policy on the two mounts* is a property of the spoke, chosen when its bastion is made for the cohort, never from inside:
** *open*: `/incoming` is readable; the human or agent reads and manipulates the data directly in the shell; `/outgoing` is visible as written.
** *sealed*: `/incoming` is a listing, names, sizes and metadata; only code that passed the gate runs against the files, as a job; `/outgoing` is shown per policy, reviewed, de-identified, or whole.
* *The loop* is edit, run, look at `/outgoing`, repeat, in minutes. Under the sealed policy the run passes the gate and executes against the real `/incoming` while the shell sees only the listing.
* *The exit* is `/outgoing` returning to ChRIS as a node of the cohort's feed; later, optionally, `plugin build` makes working code a plugin.

[[spoke-host]]
=== The host

A ChRIS that stratus puts on one VM is a stand-in spoke: the VM plays the cluster, porter is its door, and each person's berth is a container of its own with the tooling and the two mounts, so their shell is never on the machine that runs CUBE (<<berths.adoc#,berths.adoc>>; the stand-in itself is <<dev-bastion.adoc#stand-in,dev-bastion.adoc>>'s).

The host is the Hub bastion's shape with other contents (<<host>>): a container in the spoke, one per cohort, whose entrypoint starts porter; porter starts calypso; calypso spawns a pty per console; one path to the shell through chell, calypso and `!` under the `tasks` tier. calypso hosts this TD's ChRIS session with the ordinary trio, salsa, cumin and chrisapi over the CUBE API; its working directory is the project directory, and `/incoming` and `/outgoing` are mounted under the policy above. The shell holds the runtime: python, compilers, the project scaffolding, `run`, an editor for the exception. The key ring is this TD's CUBE token and nothing else: no cloud key, no kubeconfig, no `oc`. The cluster is the floor the host stands on, not a thing it operates; how the host is built and where it runs is the Hub figure's subject, not this one's.

[[spoke-common]]
=== The common case: shipped code, no human inside

In the common case the developer, human or agent, sits at the Hub, in a *Hub dev bastion*: a mise container beside the cloud controller and never the same host, holding the same project scaffolding, a door token for each spoke bastion the developer may run in, and no cloud key, no CUBE token, no kubeconfig. An edit at the Hub is shipped as source to each selected spoke's bastion over the wire, through that spoke's door, and run there unattended under that spoke's policy; `/outgoing` is what comes back. One edit, N spoke bastions, N runs, N results: the fan-out is the session's, attaching to N calypsos, not a fleet controller's. <<redhat-fl.adoc#mechanisms,redhat-fl.adoc>> sets this beside the other mechanism, shipping the code as a HARBOR app, and says why the app path is wrong for development: a quarter of an hour per change.

The exception is a developer who logs in at the spoke's own door and works inside it, under the open policy. Same host, a human in it.

[[spoke-not-backend]]
=== Not a backend

The spoke bastion is a host for a ChRIS session, not a world to mount. It would become a backend only if a tree of its own emerged, which would reopen the cross-backend question #977 deferred. OpenShift Dev Spaces ships a workspace container per developer on one cluster; it has no policy on mounts, no airlock, and is not multi-cluster aware (<<redhat-fl.adoc#survey,redhat-fl.adoc>>). The spoke bastion is not built on it; <<dev-bastion.adoc#why-not-dev-spaces,dev-bastion.adoc>> gives the reasons.

[[corrections]]
== What this corrects

Two lines in stratus.adoc placed the bastion inside the tenancy it builds: the bastion section's "later a small instance inside the tenancy, using an instance principal", and the open item "the bastion inside the tenancy". Both are withdrawn by this document. The bastion is at the Hub, outside; the thing inside a Trusted Domain is the development space above, and it holds no cloud credential.
