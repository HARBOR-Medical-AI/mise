[abstract]
== Abstract

A *Trusted Domain* (TD) is three layers an institution controls: a cloud tenancy, an OpenShift cluster built on it, and a ChRIS deployed on the cluster; the first are on Oracle Cloud Infrastructure (an *OCI TD*). Building one today is the job of `harbor-oci`, a Python command-line harness that turns an empty OCI tenancy into a running ChRIS by driving Red Hat's Assisted Installer, Oracle's `oci-openshift` Terraform stack and the `fnndsc/chris` Helm chart.

This document designs *stratus*: the second backend that issue #977 made room for. A stratus session is *outside* any ChRIS. It reads and changes the substrate — a tenancy's compartments, limits, networks, DNS, buckets, instances and clusters — and builds Trusted Domains on it, with the shell, the console, ARGUS's frame and the session host that ChRIS sessions already have. The cloud is a *driver* inside stratus, not a backend of its own: OCI is the first driver, and a second cloud adds a driver, never a backend. `harbor-oci`'s README names this direction: "building a cluster becomes one more mise backend, with a web interface and a console for `oc` and friends".

It builds on `docs/backend-neutral.adoc` (#977), whose engine, descriptor, registry, tasks and ARGUS compositions it uses, and whose two rules it keeps: one backend per session, and nothing changes for a ChRIS user. *Status: proposal revised with the operator 2026-10-20 (first draft 2026-10-10). Nothing is built before the operator approves the revision.*

[[names]]
== The name

The word for a layer cloud, and the sound of *stratum*: the layer a thing rests on. One word names three things, as `chris` does for the ChRIS backend: the package `@fnndsc/stratus`, the backend id `stratus` the attach handshake carries, and the ARGUS composition `compositions/stratus/`. The first draft proposed `hearth` and a backend id `oci`; both withdrawn. `hearth` sounds like the opposite of a cloud, and `oci` named the backend after one driver.

[[two-sessions]]
== Two sessions, two places

A Trusted Domain has an outside and an inside, and mise gives each its own session:

[cols="1,2,2",options="header"]
|===
| | The substrate session | The domain session
| Backend | `stratus` (this document) | `chris` (today's)
| Connected to | a cloud tenancy, through the driver's credential (OCI: an API-key profile) | the CUBE the build produced
| What it acts on | compartments, limits, networks, DNS, buckets, instances, the OpenShift cluster | feeds, plugins, files, PACS
| Who uses it | whoever builds and runs the domain | researchers and clinicians inside it
| Credentials it holds | cloud API key, Red Hat service account, cluster admin | a CUBE token
| Brand | the TD mark in the driver's ring (OCI: Oracle red) | the TD mark, and a domain segment in the prompt
|===

They are separate calypso daemons, as #977's <<backend-neutral.adoc#one-backend,one backend per session>> requires: one process never holds cloud credentials and a CUBE token together. ARGUS can show both as two attached sessions; the substrate session hands off to the domain session when a build finishes (<<handoff>>).

[[bastion]]
=== The bastion, and chell as the surface

The substrate daemon runs on one host, the *bastion*: the machine that holds the cloud credential, the Red Hat service account, the SSH key and, once a domain is built, its kubeconfig. It is a host at the Hub Trusted Domain, outside every tenancy it builds: the operator's workstation today, a container on the Hub cluster later (<<bastion.adoc#,bastion.adoc>> draws it). Nothing else ever holds those files.

chell on the bastion is the surface that drives a Trusted Domain: `suggest`, `domain new`, `domain plan`, `domain build`. ARGUS drives it the same way, because since #1125 the ARGUS console is a chell running on the daemon's host under a pty: typing in the browser is typing at the bastion. There is no web-only path to start a step; a control on a pane or on the controller (<<controller>>) runs a console line, as #1082's law says a view is a script. What ARGUS adds is watching and shaping: tiles, the domain pane, the log view, the controller, the brand.

[[three-layers]]
=== Three layers, three tools, one spec

Each layer has a tool today: the cloud is Terraform and the SDK; the cluster is the Assisted Installer and `oc`; the application is Helm and the seed. The first draft described the cluster in a spec and the application only as three step names and a chart version, so "deploys ChRIS to it" had nothing to deploy from. One spec, two halves: `spec.yaml` holds the cluster (CPU family, control-plane and worker pools in vCPU and GiB, boot disks) and the ChRIS on it (chart version, `dataGib`, `databaseGib`, `queueGib` as `harbor-oci` already has them, the compute backend, the PACS to connect, the seed users). `domain plan` prices and checks both; `domain build --through verify` builds the machine, `domain build` to the end installs the application.

[[findings]]
== What exists: harbor-oci

Surveyed in `~/src/harbor-oci` on 2026-10-10; unchanged since (last commit 2026-10-08). A Typer CLI (`harboroci`, `cli.py`) wrapped by a `justfile`; `just install` runs the build in order: `preflight cluster iso infra-plan infra-apply dns manifests hosts run postinstall verify` (`justfile:22`).

[cols="1,3",options="header"]
|===
| Step | What it does
| preflight | Tools present (`terraform`, `oc`, `helm`, `dig`); no secrets inside the clone; API key, compartment, attribution tag namespace; the spec fits per-AD limits and three flexible load balancers are free; DNS delegation; the Red Hat account; the SSH key (`preflight.py`).
| cluster | Creates the Assisted Installer cluster and infra-env (`steps.py`, `assisted.py`, `redhat.py`).
| iso | Downloads the discovery ISO into an Object Storage bucket and makes a pre-authenticated request for it (`ocistorage.py`).
| infra-plan | Fetches the `oci-openshift` stack (SHA256-pinned), writes tfvars from `spec.yaml`, `terraform init` and `plan` (`stack.py`).
| infra-apply | Refuses a plan that updates or destroys existing resources, then `terraform apply`. *Billing starts here.*
| dns | Upserts the `api`, `api-int` and `*.apps` records in OCI DNS (`ocidns.py`).
| manifests | Pushes the stack's custom manifests (OCI cloud controller and CSI drivers) to the Assisted Installer.
| hosts | Waits for the hosts to register (up to 45 minutes), assigns roles.
| run | Installs OpenShift (up to 120 minutes, polled each minute); saves the kubeconfig and the kubeadmin password.
| postinstall, teardown | Placeholders (exit 2, "not yet proven").
| verify | Ten live checks through `oc` and `dig` (`verify.py`).
| chris-deploy, chris-seed, smoke, chris-nuke | Helm install of ChRIS, a seed job, the smoke suite, removal (`chris.py`).
|===

Read-only verbs beside the build: `status`, `deployed`, `burn` (spend so far), `capacity`, `shapes`, `spec`, `suggest` (sizing).

* *OCI access* is the Python SDK: Identity (tenancy, compartments, tag namespaces, availability domains), Limits, DNS, Object Storage, Compute, Block Storage, Load Balancer and Resource Search ("all resources where compartmentId = …"). Terraform builds the VCN, subnets, security groups, load balancers, image, instances, dynamic groups and policies. `oc`, `helm` and `dig` run as subprocesses; the Red Hat APIs over REST; prices from Oracle's public price list.
* *Authentication* is an API-key profile in `~/.oci/config`; the region is forced from settings. Settings come from the environment over `config.local.env` over `config.env` (`OCI_REGION`, `OCI_PROFILE`, `OCI_COMPARTMENT_OCID`, `BASE_DOMAIN`, `CLUSTER_NAME`, the Red Hat credentials, pinned versions).
* *State* is `state/harbor.json` (cluster and infra-env ids, the ISO object and its link; mode 600, written atomically), Terraform's state in the staged stack, and credentials in `state/auth/`.
* *One region, one domain:* `us-ashburn-1`, base domain `oci.chrisproject.org`, cluster `harbor`. Nodes spread one per availability domain.

`harbor-oci` was a test harness: it proved the build once, live. It is the specification stratus's steps are ported from and checked against, never a dependency stratus runs (<<port>>).
* *The cloud seam already exists there:* `TenancyProvider` (`capacity.py`) and `PriceProvider` (`pricing.py`) with OCI subclasses, and a spec in vCPU and GiB. Its own analysis: "Roughly 70 percent of the code is bound to OCI" and "The install path makes no attempt at a cloud abstraction. The tenancy tools do" (`docs/overview.adoc`).
* *Known open problems:* OCI's automatic `Oracle-Tags` make a re-plan want to alter 24 resources, so `infra-apply` refuses alterations and clean re-plans are undecided; `teardown` has never been run, and the compact cluster has billed about $0.71 an hour since 2026-10-07 (`docs/status.adoc`).

[[precedent]]
== Argue from the tree that exists

The first draft drew its tree from `harbor-oci`'s shape and invented three roots (`/tenancy`, `/regions`, `/domains`). The operator saw at once that a ChRIS session already has a place for a remote world: `/net` (`/net/pacs/queries/<query>/<study>/<series>`), with processes under `/proc` and executables under `/bin` (`chris/navigation.ts`, `CHRIS_STRUCTURAL_PATHS`). *Every path, item kind and verb in this document is checked against what a ChRIS session mounts before it is proposed*, and a proposal names its precedent. A new backend joins a tree; it does not redraw one.

[[decisions]]
== Decisions

Each was put to the operator on 2026-10-20 and agreed unless marked otherwise.

[[one-backend-many-clouds]]
=== D1. One backend, clouds as drivers

Two shapes were weighed. *A backend per cloud* (`oci`, `aws`, `gcp`, …): four trees, four prompts, four compositions saying DOMAINS, CAPACITY and STEPS, and a fifth package for what they share. *One substrate backend with the cloud as a driver inside it*: the tree, the `domain` verbs, the task source, the prompt segments and the ARGUS composition written once; a cloud is a set of providers behind one interface, which `harbor-oci` already drew. The second is chosen.

What differs between clouds, as the session sees it, is small and named: how containers nest and what they are called, where a region sits, the credential and identity, the limits, shapes and prices, the infrastructure plan and apply (a per-cloud Terraform stack). The Assisted Installer and the Helm chart are the same on every cloud. <<tree>> says how four clouds map onto one tree.

The caution from #977 applies with more force: an abstraction drawn from one cloud takes its shape. Three guards:

* *A driver interface and a ratchet.* `CloudDriver` lives in `src/cloud/driver.ts`; OCI implements it in `src/cloud/oci/`. The count of files outside `cloud/oci/` that import an `oci-*` package starts at zero and may never rise (`lint:stratus-deps`, built like `lint:core-deps`).
* *A fake driver.* An in-memory cloud (`src/cloud/fake/`) runs the same driver contract suite the OCI driver runs, so the interface stays real with one cloud, as fond's null provider does for the filesystem.
* *No second driver is written before a second cloud is real.* The fake is a test, not a product.

[[package]]
=== D2. The package `@fnndsc/stratus`, and how a daemon hosts it

`packages/stratus/` in this repository while the descriptor is still settling, as #977's cautions advise. It depends on brasa's core (`@fnndsc/brasa/core`), fond, menu and calypso, and on Oracle's TypeScript SDK as per-service packages (`oci-identity`, `oci-limits`, `oci-resourcesearch`, `oci-objectstorage`, `oci-dns`, `oci-core`, …) rather than the whole `oci-sdk`. It never loads cumin, salsa or chili; CI gets a stratus boot beside brasa's core boot that fails if one is loaded.

*How calypso hosts it.* Four ways were weighed: calypso depending on stratus (every ChRIS install would pull the OCI SDK: wrong direction); calypso importing `@fnndsc/<id>` by flag (an allowlist and a version-skew problem); a config file mapping ids to modules (the same, with more machinery); and *stratus shipping its own launcher*. The last is chosen for now: the `stratus` command imports calypso's `daemon_launch`, creates the engine with `engine_create(stratusBackend_make(...))`, and hosts it. Nothing in calypso changes, the dependency arrow points from stratus to calypso, and #977's picture already drew it ("chell, porter and the calypso launcher each compose the engine with exactly one backend"). A substrate daemon is started by hand on the host that holds the cloud credential. porter starting one is deferred with porter's second tier, and brings its own question: a substrate session has no CUBE password, so its door is a different thing.

[[port]]
=== D3. Everything in TypeScript; harbor-oci is the specification, not a dependency

Decided 2026-10-22, replacing "wrap the build, port it step by step". Under that frame every build step would have run chell → brasa → stratus → runner → `uv` → Python → SDK or Terraform: a Python runtime on the bastion, a second state file (`harbor.json`) for stratus to parse, progress only as text, and steps that never become driver methods a second cloud's driver also implements. `harbor-oci`'s Python is orchestration over calls stratus can make itself.

* *Everything that reads* — the tree (<<tree>>), limits, capacity, shapes, prices, spend — is written in stratus against the SDK.
* *The build steps are the driver's own code from the first.* The Red Hat Assisted Installer and the OCM token over `fetch`; Object Storage, DNS and the rest through the SDK clients. What `harbor-oci` proved transfers as the specification: the order of the steps, the refusal of a plan that alters existing resources, `Oracle-Tags` drift, one node per availability domain, the ISO and its link, the custom manifests, the waits (45 minutes for hosts, 120 for the install).
* *Terraform runs in OCI Resource Manager, not on the bastion.* The `oci-openshift` stack is a Resource Manager stack (its `schema.yaml` is the Resource Manager form). The driver creates the stack from the pinned release, runs a plan job, reads the plan as JSON (`getJobTfPlan`, format `JSON`) for the alteration check, runs an apply job, and reads the job's log and outputs. Terraform's state stays in Resource Manager. There is no `terraform` binary on the bastion.
* *`verify` without host tools:* `oc`'s checks become Kubernetes API calls through the cluster driver (<<tree>>); `dig` becomes `node:dns` against the zone's own name servers and a public resolver.
* *Helm is the one host program the build may still need,* for the ChRIS half (step 5); decided when that step is reached (<<open>>).
* *Three driver kinds, the steps written once over them* (decided 2026-10-22). The cloud driver (`cloud/`, OCI first): limits, storage and its links, the infrastructure plan and apply, DNS, and the platform manifests (`manifests_of`, which returns the files and pushes nothing). The installer driver (`installer/`, the Assisted Installer first): the cluster and infra-env, manifest upload, the host wait and roles, the install, the kubeconfig; one implementation on every cloud, as `cluster/` is, and a hub's Hive or a Cluster API provider would be a second installer. The cluster driver (`cluster/`): verify's checks. `domain/steps.ts` names the steps and their order and calls the drivers; a second cloud adds a cloud driver, not steps.

[[tree]]
=== D4. The tree: a tenancy is a mount under `/net`

Precedent: `/net/pacs/queries/…` is a remote server and then what it holds. A cloud tenancy is a remote filesystem the session mounts, as NFS mounts under `/net`.

* *One shape for every cloud:* `/net/<cloud>/<root>/<container>/…/<kind>/<name>`. Four clouds map onto it; what differs is how containers nest, where a region sits, and what a zone is called.
+
[cols="1,1,2,2,1",options="header"]
|===
| Cloud | Root | Containers (nest) | Region | Zone
| OCI | tenancy | compartments, any depth | orthogonal to compartments; an API client per region | availability domain
| AWS | account (alias, else id; or the organization) | none below the account: resource groups are tag views | the primary partition; an API per region | availability zone
| GCP | organization | folders, then a project | an attribute of a resource | zone
| Azure | tenant | management groups, a subscription, a resource group | an attribute of a resource | availability zone
|===
+
The path carries names only; the container noun (compartment, account, project, folder, subscription, resource group) is the row's type in `ls -l`. The driver answers `containers_list(parent)`, so OCI nests arbitrarily, Azure three fixed levels, AWS none, under one path grammar.
* *Region is the session's, not the path's.* The session has one region (<<prompt>>, the `region` verb), and the tree lists that region's resources; `regions/` under the root holds every region's facts; global kinds (DNS zones; buckets on AWS and GCP) list regardless. Every resource has a `region` field. A region segment in the path would be real on AWS and faked on OCI and GCP, and an `ls` on AWS that fanned out over twenty regions would never be quick; `harbor-oci` already forces one region, so OCI loses nothing.
* *Kind folders are generic nouns; native detail is in `info.json`.* Every cloud has `instances networks subnets securitygroups loadbalancers volumes buckets dns`, so the `domain` verbs and the tiles touch only those. A driver may add native kinds nobody else has (OCI: dynamic groups) as extra folders. OCI's NSGs are `securitygroups`, its availability domains are `zones`.
* *No new root.* Only `/net/<cloud>` is claimed, and a session has one cloud. `/net/oci` lists one tenancy today (one API-key profile is one tenancy); the level stays because the path says which tenancy you are in, and `~/.oci/config` can hold several profiles. Whether one session should ever mount two is a posture question for later; the shape allows it.
* *Everything under the tenancy.* Limits are per tenancy per region; a domain is built in one tenancy. So `regions/` and `domains/` sit inside `/net/oci/<tenancy>/`, one rule, rather than beside it. Shapes and prices repeat per tenancy, harmless with one.
* *Compartments beside kind folders.* `/net/oci/fnndsc/` holds child compartments and the kind folders at one level, as OCI's own compartment view does; `ls -l`'s type column (`compartment` against `instance`) tells them apart. The kind folders are reserved names: a compartment called `instances` shows as `instances~<last six of its OCID>`.
* *Kinds in the tree, first:* `instances networks loadbalancers volumes buckets dns`; subnets and security groups nest under their network. Images, policies, dynamic groups and tag namespaces stay out until a verb wants them; they appear in a parent's `info.json` where OCI returns them.
* *Field files.* Every kind: `name id state region created tags info.json`. Per kind on top: an instance `shape zone ips`, a volume `size attached`, a load balancer `ip shape`, a bucket `links` (its pre-authenticated requests, one per line: object, name, access, expiry; OCI returns a link's URL only when it is made). What a resource holds sits in a folder beside its fields, so no name it holds can collide with a field: a network's `subnets/` and `securitygroups/`, a bucket's `objects/`, a zone's `records/`. The rule `/proc/jobs` follows: a field is a file when a shell line wants it (`cat state`, `grep running`); everything else is in `info.json` only.
* *Names, not OCIDs, in paths.* The OCID is the field `id`. OCI allows two resources in one compartment to share a display name, so a duplicate shows as `name~<last six of its OCID>` and the plain name refuses ("ambiguous: name~1a2b3c, name~9f8e7d"), never picks one. The rule holds wherever a path is resolved: `cd`, completion, globbing and `@N` expansion.
* *Structural paths* (`cd` without a lookup, as `CHRIS_STRUCTURAL_PATHS`): `/net`, `/net/oci`, `/net/oci/<tenancy>`, each kind folder, `regions`, `domains`.
* *The cluster is under its domain*, not a root of its own: built in that tenancy by that domain's steps, reached with that domain's kubeconfig. The Kubernetes driver that serves it is the same on every cloud, so it is a second driver kind (`cluster/`) beside `cloud/`, never inside a cloud driver. The linux-metaphor note already drew it ("projects as folders; deployments, pods and routes as entries in them"). Read-only in the tree; `oc` and `helm` under the `tasks` tier are the write path. This closes the first draft's open question of `oc` against a Kubernetes provider: both, each for what it is good at.
* *A domain read from a `harbor-oci` checkout* (`stratus --domain harbor=~/src/harbor-oci`): `harbor-oci` keeps no history of its steps, only what each leaves for the next (the Assisted Installer ids, the ISO link, the staged stack and its Terraform state, the kubeconfig). A step's `state` is read from that evidence and its `evidence` file says what it rests on: `done`, `not done`, `expired` (the ISO link), or `unknown` for a step whose result the host does not keep (preflight, dns, manifests, hosts, verify). `settings` shows only the cluster's name, base domain, region, compartment and pinned versions from `config.env` and `config.local.env`; `state.json` withholds the ISO link's URL; the Terraform state is counted, never shown. This is the first half of *adopting* a domain `harbor-oci` built: the build steps (<<order>>, step 4) import its Assisted Installer ids and its Terraform state (a Resource Manager `ImportTfState` job) once, and from then on the domain's state is stratus's own and the checkout is no longer read. Adoption runs a plan only: an apply against an adopted domain is refused until it is allowed by name. A clean adoption plans no creations and only `Oracle-Tags` changes, the best test of the drift check with nothing running touched. The first real build is proven on a new domain in a scratch compartment (decided 2026-10-22).
* *A domain's state lives on the daemon's host,* under `$XDG_STATE_HOME/stratus/domains/<name>/`: `spec.yaml`, `state.json` (the ids and each step's history, written atomically, mode 600) and `auth/` (secrets, mode 600, refused over `/vfs`); `domains/<name>/` is a view of that folder. The build puts the domain's attribution tag on its Resource Manager stack, so a fresh bastion with the same key finds every domain through Resource Search and rebuilds its ids and step states read-only, never its secrets (the kubeconfig is fetched again from the Assisted Installer). Decided 2026-10-22.
* *Home is the tenancy's `domains/`*, because building and running domains is the session's purpose; the prompt shows it as `~`. `/home/<user>` is the core's and holds the operator's own files.
* *Listings walk.* A compartment can hold thousands of objects; the tree follows the house rule that an unbounded ask walks and a bounded one says what it shows. Listings cache with a short life, refresh in the background, say when they serve a cached answer, and `--fresh` forces, as ChRIS listings do.
* *As read live on 2026-10-20* (slice 1a, read-only): the tenancy `fnndsc-bch`, one compartment `harbor-oci`, one region, three availability domains named `<prefix>:US-ASHBURN-AD-n`, 128 services with limits, 830 compute limits (zone and region scoped), 68 shapes, 15 priced; the whole walk in about six seconds, each answer then cached for a minute.
* *Disconnected.* No `~/.oci/config`, a missing profile or a refused key: the daemon still starts, with identity `disconnected@oci` (ChRIS: `disconnected@no-cube`). `/net/oci` lists empty with one note, `ls` elsewhere works, the `domain` verbs refuse "not connected". The credential is a file on the host, not a password, so there is no in-session login: fix the profile and restart.

[[rows]]
=== D5. What a row is: numbered as a folder, drawn as a resource, labelled by the cloud

Three fields of a listing row do three jobs, and only one gains anything new.

* *Numbering kind* (`answerKinds`, `@KIND N`). An index expands to a path; the kind says what a verb may be handed and whether a group row hands on its children (ChRIS: `pull` takes SER, STD and PAT and refuses a DIR; a study handed whole gives its series). Every stratus row is a path and no stratus verb needs to refuse by kind or expand a group, so stratus registers *no kinds*: rows are DIR and FIL, `cd @3`, `cat @2/state`, `domain build @1` work by path. A kind earns its place when a listing's rows are not paths or a verb must refuse by kind; the first such listing is `domain plan`'s output, where one change among the `Oracle-Tags` drift must be nameable (`--allow @CHG4`). That kind arrives with that verb (<<order>>, step 4), not before.
* *Item type* (`ListingItem.type`, an open string; the backend's `ListingLook`). How `ls -l` draws the row: mark, colour, container, size column. Stratus adds the container nouns (`compartment`, and on other clouds `account project folder subscription resourcegroup`) and `instance network subnet securitygroup loadbalancer volume bucket object dnszone record domain step`, and for the cluster `node operator project deployment pod service route pvc configmap`, coloured by lifecycle state as jobs are by status: running green, stopped dim, provisioning amber, failed red.
* *The first thing stratus showed the core was wrong* (<<cautions>>, "the descriptor will move again"): `cd`, `ls` of a file and a read that failed on a folder decided folder-ness by naming item types (`dir`, `vfs`, `job`), so a compartment could be listed but not entered. The tools now ask the installed look through fond's `itemType_isContainer`, and the dispatcher is told the same test when the engine is created. A ChRIS session is unchanged: its jobs were already containers in its look (slice 1a, 2026-10-20).
* *Tags* (`ListingItem.tags`). ChRIS fills it with a user's tags on files (`/proc/tags`). Stratus fills it with the cloud's tags, freeform and defined, so the attribution tag (`openshift-tags.openshift-resource=<domain>`) shows in `ls -l` and `grep` over a listing (#1101) finds every row a teardown would take.

[[writes]]
=== D6. Read-only by default; a domain changes through plans

The substrate bills by the hour and some of it cannot be recreated. The session therefore changes the cloud only in ways that say what they will do first:

* *The core file verbs mutate only data:* objects under `buckets/<bucket>/` (`cp`, `rm`, `mv`, `>`; large objects stream both ways through the descriptor's `files.stream`) and records under `dns/<zone>/` when the zone is a domain's own. On any other resource they refuse by name ("rm: /net/oci/fnndsc/harbor-oci/instances/node-0: Operation not permitted: a domain's resources change through `domain`").
* *A record is a file per record name* (`api`, `api-int`, the wildcard), its content the record set as zone-file lines; `>` replaces the set. The wildcard's file name is settled with the step that writes it.
* *A domain changes through `domain` verbs that plan first:* they print what will be created, changed and destroyed, with the estimated hourly cost, and ask before acting. `harbor-oci`'s rule stays: a plan that alters or destroys existing resources is refused unless the operator asks for it by name, and `domain plan` says which alterations are `Oracle-Tags` drift rather than hiding them or crying wolf.
* *Without the `tasks` tier a session changes nothing outside its own host:* no cloud resource, Red Hat record, bucket object, DNS record or cluster object, billed or free. `domain plan` without the tier goes as far as reading takes it (the fit per availability domain, the hourly cost from the price list, the steps' states) and says by name that the Terraform plan needs `tasks`; with the tier it also creates or updates the Resource Manager stack and runs the plan job. Decided 2026-10-22.
* *Drift is counted apart.* `domain plan` splits its change count: changes that are `Oracle-Tags` drift are shown as such; any change that is not drift is shown as a real change, and the apply is refused unless asked for by name.
* *Destruction is scoped by attribution.* The build tags what it creates (the attribution tag namespace preflight already checks); teardown removes only resources carrying this domain's tag, and refuses anything else even inside the domain's compartment.
* *Teardown, first form* (decided 2026-10-22, built with the first real build; widened 2026-10-29): a Resource Manager destroy job on the domain's own stack after showing its plan; then the domain's DNS records, its ISO and link, its Assisted Installer cluster and infra-env, and the block volumes the cluster's CSI driver made for its claims, which the stack never knew. Those are named by the cluster itself, read from its PersistentVolumes before the destroy: read live on 2026-10-22, OCI's attribution tag on them (`openshift-tags.openshift-resource`) holds the same value, `openshift-resource-infra`, for every cluster, so it cannot say whose a volume is; since 2026-10-29 any block volume still in the domain's own compartment carrying that namespace goes too, the compartment being the domain's, which covers a cluster whose kubeconfig this host never had. Then what carried the domain's tag, so that it is not found again: the stack itself; the compartment with the image bucket in it when stratus made them (`domains/<name>` under `domains`), else only the tag off the compartment (harbor-oci's keeps itself, with the zone and the tag namespace in it). A compartment that still holds something stays, and the log says so. It refuses a domain read from a checkout. An adopted domain is torn down as a built one is (2026-10-29; the first design refused it by name, when harbor was the only domain and the teardown unproven): its lock is the guard, `domain protect <name> off` as its own line, then the name typed back. Its question is answered by typing the domain's name, not `y`. The sweep of everything else carrying the tag stays its own design.
* *Live tests mutate only in a scratch compartment* (`zz-mise-<epoch>`), never in a compartment holding a domain, as the CUBE lesson taught.

[[commands]]
=== D7. Commands

Core commands (`ls`, `cd`, `cat`, `cp`, `find`, `grep`, `wc`, `head`, `sort`, …) work over the tree unchanged, because they use only fond's filesystem. The backend registers, in shell metaphors and with the help categories #1102 made every command carry:

[cols="1,3",options="header"]
|===
| Command | What it does
| `domain new <name> [--family F] [--plane 3xV/G] [--workers NxV/G] [--data G] [--base-domain zone]` | Writes `domains/<name>`'s spec on the host and nothing else: `harbor-oci`'s compact cluster, sized by the options.
| `domain plan [<name>]` | Preflight and the infrastructure plan; prints the changes and the hourly cost; names tag drift.
| `domain build [<name>] [--through <step>]` | Runs the build's steps in order as tasks, from the first not done; stops after `--through`.
| `domain status` | Where each step stands, and the evidence.
| `domain verify [<name>]` | The live checks, ported from `harbor-oci`'s ten. With `tasks`, all ten; without it, the nine that only read, saying by name that the block-volume probe (a claim and a pod) needs the tier.
| `domain adopt <name> [--from <checkout>] [--stack-compartment <ocid>]` | Without `--from`, keeps a domain found in the tenancy by its tag (<<found>>): its stack and compartment, the zone and spec read back from the stack's variables, no secrets; reads only, no tier. With `--from`, keeps a domain `harbor-oci` built: its ids, spec, step evidence and secrets here; with `tasks`, a Resource Manager stack of the pinned release with its variables and its Terraform state imported. Planned against, never built on.
| `domain teardown <name>` | Plans removal of what the domain built (<<writes>>), shows it, asks for the domain's name.
| `domain attach <name>` | Opens the domain session against the domain's CUBE (<<handoff>>).
| `domain [<name>]` | In ARGUS, opens the TD controller (<<controller>>); in chell, `domain status`.
| `kill <task>`, `wait <task>` | Core: ask a running step to stop (gently; a second `kill` says so), or attach until it ends.
| `limits`, `capacity`, `shapes`, `prices` | What the region allows, has free, offers and charges.
| `spend [<name>]` | What a domain has cost so far and costs per hour (`burn`).
| `suggest` | Sizes a spec from workload figures (`--workers`, `--worker-ram`, …).
| `region [<name>]` | Shows or changes the session's region; the prompt follows.
| `oc`, `helm` | Run against the domain the working directory is in, with its kubeconfig, under the `tasks` tier.

There is no `terraform` command: Terraform runs only inside `domain` steps, in Resource Manager, where its plan is checked. The `oci` command-line tool is reachable only through the `!` shell tier, like any host program; since #1096 `!` runs in the terminal's pty, so `oci` and `oc` are interactive there.

[[identity]]
=== D8. Identity and credentials stay on the daemon's host

* The driver supplies the identity. For OCI the daemon reads an API-key profile from `~/.oci/config` (`--profile`, default `DEFAULT`). There is no instance principal: the bastion never runs inside a tenancy it builds (<<bastion.adoc#posture,bastion.adoc>>).
* The identity is the IAM user's name (looked up from the user OCID) at the tenancy's name: berth `user@tenancy`, the same form on every cloud. On the live tenancy the user's name is an e-mail address (`rudolph.pienaar@childrens.harvard.edu@fnndsc-bch`): two `@` in a berth, kept as the cloud writes it rather than shortened and made ambiguous. Decided 2026-10-21: the berth is one string everywhere; the prompt shows it in full and a surface short of room truncates it from the left, as it does a path, so `whoami` and the prompt agree. The region belongs to the session, not the identity, so changing region keeps the berth.
* The Red Hat service account and the SSH key are daemon settings, as in `harbor-oci`'s `config.local.env`.
* *Secrets are never files the browser can read.* `domains/<td>/cluster/` shows `console api version nodes/`; the kubeconfig and the kubeadmin password live on the host under the domain's state, and `cat` and `/vfs` refuse them with the host path. `oc` and `helm` under the `tasks` tier read the kubeconfig on the host themselves. The console password never passes through stratus (decided 2026-10-22): it stays a file on the host, read there (`!` under `shell`, or the operator's own login); the controller says where it is, nothing more.

[[prompt]]
=== D9. The prompt says where in the substrate you are

The wire's prompt context is ChRIS-shaped (`user`, `uri`, `cwd`, `pacsserver`, `physicalMode`, `procWarmup`, and since #1128 `questions`). It gains an optional, backend-neutral list of *segments* — each a key, a label, a value and a tone — that a backend fills and the composition draws in order. ChRIS's fields and prompt do not change; an older daemon sends no segments and an older surface ignores them.

The stratus prompt, the leader segment from the driver:

[literal]
....
◆ OCI │ fnndsc │ us-ashburn-1 │ rudolph │ harbor │ ~/harbor/steps │ 4s
       tenancy   region         user      domain   working directory  last command
....

The domain segment appears when the working directory is inside a domain or one of its resources. A running step adds a segment with its name and progress. Disconnected, the leader reads `OCI ✗`. The user segment carries the identity as the cloud writes it, in full; a surface that is short of columns truncates it from the left, keeping its ending, before it shortens the path. Each segment carries a key the surface may know a glyph for, a label for a reader who meets the key cold, the value, and a tone (leader, place, identity, path, work, note, alert) the surface maps to its own palette; no colour crosses the wire.

[[tasks]]
=== D10. Build steps are tasks; the supervised runner stops being deferred

#977 deferred the supervised runner and its `tasks` tier (#986) "until the second backend actually starts". This is that start:

* Each build step is a task in stratus's task source, under `/proc/steps` and in the domain's `steps/` folder: state, structured progress, log tail, start and end.
* *The runner is in the daemon, and a step is the driver's own code,* not a host process (<<port>>): requests, Resource Manager jobs and polls. The runner keeps a step's full log on the host, survives a closed browser and a closed chell, and reattaches. A step whose work runs in the cloud (a Resource Manager job, the Assisted Installer's install) survives a daemon restart as well: the runner finds it again by the id the step recorded and resumes polling. It is *not* the terminal's `!` path (#1096): that runs a child of one chell under one pty and dies with it; a step outlives any surface.
* A step's live state travels as the wire's `event` message (kind `stratus.step`, added by #1157 for trek) when a pane wants more than the progress schema carries; the progress schema carries what the prompt and the tiles need. Decided when the first pane is drawn.
* *Cancelling is gentle.* Terraform interrupted mid-apply can leave state locked or half-written: cancel asks Resource Manager to cancel the job without forcing it, and Terraform finishes its current operation; a second cancel says so instead of escalating.
* *The runner is brasa core's* (decided 2026-10-22, as #977 drew it): `core/runner.ts` starts a job the backend hands it, an async function given a progress callback, a log writer and a cancel signal; it keeps each job's record and full log under the daemon's state folder and is itself a `TaskSource`, so `/proc/<id>`, `cat log` and the tiles come free. The backend supplies a `resume(record)` hook for a job whose work runs in the cloud. `kill` and `wait` are core commands. Stratus supplies the steps; ChRIS registers none.
* *The `tasks` tier is a launch-time gate on spending,* off by default, separate from `shell` (the tiers today: `shell`, `files`, `pipes`), enforced at core's door where `shell` is, so no backend starts a job past it (decided 2026-10-22). The steps no longer start host programs; what the tier guards is the cloud and the bill. It and the question a billing step asks are two locks, not one. A ChRIS session never enables it. Launch-time means fixed for the session, not hidden behind a flag (decided 2026-10-29): through porter the person entering is asked at the door, READ or MANAGE, the way trek asks its settings before the first turn, on both surfaces alike (<<d14>>); nothing inside the session raises it, and changing the answer is entering again.

[[controller]]
=== D13. The TD controller: a screen over the engine, as the trek bridge is

`docs/trek.adoc` built a full-screen ARGUS surface over an engine without changing the engine: the engine shows its state before each prompt, a typed `event` carries it, the bridge takes the screen, and plays by answering the engine's questions with lines built from its controls; nothing moves without an engine line behind it. The TD controller is that pattern over the domain machine:

* *The engine* is stratus's domain machine, already driven by console lines (`suggest`, `domain new`, `domain plan`, `domain build`, the questions it asks before billing).
* *The state shown:* a `stratus.domain.state` event before every prompt and on every change: the spec, each step's state and progress, the cost so far and per hour, the cluster's readiness, and what changed since the last event (the diff the trek header shows). Built as: `domain status` answers each domain with what the controller draws (its condition, whether it bills, built, adopted or read from a checkout, what is refused on it and why, the spec, each step with its times, the build's task, the last plan counted with drift apart, the last verify check by check, the open question), and `domain build` shows its domain as that event at its start, on each line it logs and before each question, from the host alone (no live counts, no cost); the controller reads `domain status` when it opens and after each line, and the event between.
* *A takeover.* `domain` with no arguments in the ARGUS console opens the controller full screen; LEAVE returns, as trek's bridge does. Same reasons as trek's "why a takeover": a build holds the lane for two hours, and a pane among panes would mislead. In chell the same lines play as text.
* *The screen,* in trek's layout under ARGUS's theme: the header carries the domain's condition, its cost and the time in the current step (settled below); the gutter holds the views, OVERVIEW, SIZE, BUILD, CLUSTER, CHRIS, TEARDOWN and LEAVE; a view changes the body, a command works in place. SIZE is `suggest` as controls: sliders for workers, worker RAM, ChRIS data, with fit and cost live from `regions/`; `domain size [--family F]` reads once what a new domain is sized against (each zone's free cores and memory, the family's shape and price, storage and load-balancer prices, the starting spec), and the controller redraws from it as the levers move. BUILD is the steps as a strip, the running one with its log. CLUSTER and CHRIS read `cluster/`. TEARDOWN is the attribution-scoped plan and its question.
* *The controls follow the value.* A slider commits as `domain new --workers 2 …`; BUILD's pill sends `domain build <name>`, as far as the steps go; the engine's "billing starts at this rate, continue?" is answered by a pill and never skipped. Nothing on the screen starts anything without a console line behind it: #1082's law, and trek's `a-frame-replays-a-printed-line`.
* *The one difference from trek:* a game dies with its surface, a build does not. The controller attaches to a step already running, so the state must be replayable on attach: the task source is the baseline, the event the delta. Trek's event is live only; this one is not.
* *Order:* a mockup page first, grilled, as trek's was; built after step 4 (<<order>>), when the runner and the steps it drives are real. The tiles of <<argus>> are the glance; the controller is where a domain is worked on.
* *Mockup:* https://claude.ai/artifact/L4nAHMfFqmHYytnnUReuo2[the TD controller canvas], v2 after the grill of 2026-10-22 (private to the operator until shared): OVERVIEW, SIZE, BUILD at the plan and running, CLUSTER, CHRIS, TEARDOWN, and a re-plan with drift.

Settled on the mockup, 2026-10-22:

* *The header,* on every view: CONDITION, DOMAIN (tenancy, region and compartment, address), COST (per hour, so far, the month), BUILD or STEP (last done, running, last plan), and SINCE LAST COMMAND (the diff).
* *Eight conditions:* SIZING, STOPPED, ASKING, BUILDING, UP, SERVING, FAILED, GONE. STOPPED is a build left part way (steps done, none running, not up); its line says PLANNED when the next step is the first that bills. Billing is not a condition: it is an orange line under the pill whenever money runs. Orange means billing everywhere on the screen; red means destroying.
* *Domains as pills* under the backend's block in the upper gutter, one per domain and a NEW; a pill sends `domain <name>`.
* *A prompt at the foot,* under the session's log: the one departure from trek, whose ship's log is read-only. Any session line may be typed there, as at the console (`ls cluster/`, `oc get pods` under `tasks`, `domain plan`); its output joins the log and the board redraws from the state event as always. The controls send the same lines.
* *Steps* are a grid with each step's evidence on OVERVIEW and a rail beside the running step on BUILD; a step pressed on OVERVIEW opens BUILD on it. A line marks where billing starts.

* *A re-plan* shows drift apart from real change in its count (<<writes>>).
* *Heard and titled:* a step ending, the engine asking and a failure are cues in ARGUS's synthesized voice, and the tab title carries the condition (`ASKING · trial`). Nothing leaves the browser.
* *Entry:* `domain [<name>]` in ARGUS's console, or the DOMAINS tile: the tile pressed sends `domain`, a row on it `domain <name>`.
* *Desktop only, for now:* under about 1250 px the controller does not take the screen and says so; the line runs as text. A narrow design is its own round.

Built 2026-10-23 (the readouts #1224, the screen after it): `domain` and `domain <name>` are claimed by ARGUS under stratus (every other `domain` line stays the session's); the controller reads `domain status` on opening and after each line, and the build's `stratus.domain.state` events between; SIZE reads `domain size` once and redraws fit and cost as presentation; CLUSTER shows verify's checks and the compartment's counts, and its nodes and projects wait on the cluster in the tree, as CHRIS's SMOKE AGAIN and ATTACH do.

| A tenant as a manifest | A shared `tenant.mise` (`@param NAME`) is the procedure: `domain build` through `smoke`, `expect` claims on its steps and its verify, and `@answers` with the domain's status. It starts from a written spec and never writes one (settled 2026-10-23): `spec.yaml` stays the only truth of what a domain is, so the size reaches the build through `domain new` and never through the manifest's parameters, which are single words. It ships with the engine and stands in the session's home beside the domains (`~/tenant.mise`), as a ChRIS manifest stands in its home. NEW DOMAIN's COMMIT sends `domain new <name> …`, then `play ~/tenant.mise --param NAME=<name>`; headless, the same two lines build a tenant.
| Claims | `expect` and `play` come back to core in a backend-neutral form: core keeps `expect`'s grammar, `--within`, the verdict model and `path exists|count`; each backend registers its subjects (ChRIS `gather`, `feed`, `run`, `path … tags`; stratus `domain`: `verify`, `step`, `cost`); `play` reads a manifest through the backend's files or the engine's disk. Today both are in the ChRIS group (#1001), so a stratus session has neither.

[[found]]
=== D15. The tenancy is the truth about its domains (settled 2026-10-26)

A session lists every Trusted Domain the tenancy holds, not only those its own folder keeps. Found live on pangea: the operator's first stratus session through porter read DOMAINS · NONE while the tenancy held `harbor`, built by harbor-oci, adopted on 2026-10-22 and costing $0.71 an hour; the tag the build and the adoption put on its stack and compartment, `mise-domain=<name>`, was there for rediscovery and nothing read it. Every new user of a tenancy with a domain in it would have seen the same empty tile.

* *The tenancy is the truth.* `domain status` and the TRUSTED DOMAINS tile list every stack and compartment tagged `mise-domain`, found by one Resource Search across every compartment the key can see (`domains_find` on the driver), one domain per tag value, from its stack when one exists, else its compartment. No stack and no compartment: not listed. A domain this host keeps nothing of is read from the cloud alone (`domain/found.ts`, 2026-10-29): its address and spec from its stack's variables (`stack_describe`), else the tenancy's only zone for the address; its condition from what lives in its compartment and what its stack still holds: UP when machines live, STOPPED when none do but the stack holds something, GONE when nothing lives and the stack is empty or there is none; its steps as far as the cloud attests them (the compartment when one carries the tag, the apply when machines live), the rest `unknown` while it stands and `not done` when it is gone. Seeing never waits on adoption: the first design coupled the two because one host and one operator held every domain, and through porter every user but the builder would otherwise see every domain as FOUND forever.
* *Finding does not adopt.* `domain adopt <name>` with no checkout writes the folder from the stack: its id, its compartment, the zone and the spec its variables say, `infra-apply` done when machines live in its compartment, and no `auth/`: no cloud read recovers a kubeconfig or a CUBE token, so those are copied by hand before `domain verify` or `attach`. It is then ADOPTED · PLANS ONLY, as harbor is. Reads only, so the `tasks` tier is not needed.
* *Porter keeps each stratus session's private state folder*, on both doors; with the two points above an empty folder costs one `domain adopt`.
* *A found domain answers reads and `domain adopt` only.* `plan`, `verify`, `build`, `teardown` and `protect` are refused by name with "adopt <name> first": adoption is where the session takes responsibility for acting on a domain, and the name-typed confirmation of a teardown was designed for a domain the session knows. The one exception is a found domain with nothing left of it but its tag (GONE): `plan`, `verify` and `build` are refused as pointless, and `domain teardown <name>` is taken without an adoption, since there is nothing a lock would keep; it writes the record (unprotected, adopted from the tenancy), asks for the name typed back, and removes the tag's carriers (<<writes>>, teardown). The controller offers it as REMOVE WHAT IS LEFT.
* *The tree lists what the host keeps.* `domains/<name>/` under the tenancy still stands for the folders on the host; a found domain has no folder until it is adopted. Listing found domains in the tree is a later slice.

[[foundations]]
=== D16. Foundations, then what is built into them; the script is the truth (settled 2026-10-31)

Settled with the operator 2026-10-31, from the need to bring `cube.chrisproject.org` back (NERC unreachable since 2026-10-28) as a VM in the tenancy. The store was built once by hand and torn down the same afternoon (<<howto-store-vm.adoc#,howto-store-vm.adoc>>): it is to exist only as code, and that run is the specification the verbs below are written from.

*Foundation first, then build into it, everywhere.* stratus is the general surface over a tenancy, and ChRIS is one layer on top of what it builds. A foundation is a thing with no application on it: an *OpenShift* cluster, a *VM*, later OKD (a second installer driver, the same cluster kind), OKE (plain Kubernetes, managed) or SLURM, each only once it is real (the rule <<one-backend-many-clouds>> keeps for clouds). *ChRIS* is a layer that targets a foundation. A *Trusted Domain* is a recipe, OpenShift and then ChRIS on it, as `tenant.mise` already plays it: not a fourth kind of machine. The dashboard shows them as OPENSHIFT, VM, CHRIS and TRUSTED DOMAIN; CHRIS with no foundation in the tenancy says "first build a VM or OpenShift".

*The rename.* "Domain" has meant the bare cluster in the verbs (`domain new`, `domains/`, the tag `mise-domain`). Under this split the word belongs to the composite: the bare cluster's verbs become `cluster`, and `domain` means the Trusted Domain recipe. Done first, as its own change; the sections above keep the word `domain` where they describe those verbs as first built, and read as `cluster`. The folder is `clusters/`, the tag `mise-cluster`. The cluster build stops at `verify` once the ChRIS layer's `chris deploy` exists: `chris-deploy`, `chris-seed` and `smoke` move there with it.

*The script is the truth.* One `.mise` script, in git, states what should exist, in words every cloud understands, and runs unchanged on any cloud a driver exists for, as a CUBE workflow is one spec for every substrate. The store's:

[source]
----
net new chrisproject-services --cidr 10.20.0.0/16
vm new store --net chrisproject-services --open 80,443 --vcpu 2 --memory 8 --disk 50 --data 50 --data-backup daily --os ubuntu-26.04
vm build store
chris deploy store --profile minimal --compute NERC --host cube.chrisproject.org
----

This amends D14's "the manifest is the procedure, never the shape" for concrete scripts: a concrete script is the shape, and the `spec.yaml` its `new` lines write on the host is the record of it, never edited by hand. A procedure script (`tenant.mise`, `@param NAME`) is still only a procedure. The store's script lives with the name it serves, in `FNNDSC/chrisproject.org`; the engine stays in mise.

[cols="1,4",options="header"]
|===
| Decision | What it means

| `new` declares | `vm new` and `net new` on something that exists compare: the same values print `store: unchanged`, different ones update the record and print the change (`memory 8 → 16`). They build nothing; `build` plans and asks, and refuses a change that destroys data unless it is named. The one verb where replayable code outranks POSIX's refusal; its help says so.
| Only portable words | The script names `--vcpu`, `--memory`, `--disk`, `--data`, `--os`. The driver chooses the family (the cheapest that fits; OCI: E5.Flex), the image (the newest of that OS, pinned in the record; a later play says "newer image available" and never rebuilds silently) and the zone (the first with room). A cloud-specific override never enters a script; if one is needed it is a tenancy setting of the driver.
| The network is declared | `net new <name> --cidr` is its own line and VMs join it with `--net`: the address range collides with VPNs and peering, and the network outlives any one VM. `--open 80,443` is the portable form of a security group; the subnet, gateway and route are the driver's.
| The network carries the place | `net new chrisproject-services` is, on OCI, a compartment of that name with the VCN in it (on Azure a resource group, on AWS a tag). Every VM on the network lives in its place. A compartment of that name that already exists, empty, is adopted, not recreated.
| Shell access | The script says nothing about shells: the build needs none. `net new` builds the cloud's managed bastion (OCI Bastion; it bills on Azure, and the plan says so), admitting only the mise bastion's public address, read at build time. `vm shell <name>`, under the `shell` tier, opens a session and the tunnel in the console's pty, so typed in ARGUS's console it lands in the VM in the browser; `--print` gives the `ssh` line instead. `--open 22 --from <cidr>` opens direct SSH, declared in the script where git and the plan show it. No port 22 to the internet otherwise.
| ChRIS goes on after the build | `chris deploy` reaches the VM over the bastion path, copies the compose file and its environment, and starts it. Not cloud-init: instance user data is readable by anyone who can read the compartment's instances. The same verb serves a VM another script built.
| Secrets | The internal ones (Django, Postgres, pfcon) are generated by the first deploy and kept in the record's `auth/` on the host (mode 600, refused over `/vfs`), reused by every replay and rebuild, so a rebuilt VM opens the old database. The admin password is asked once by a typed question ("admin password for chris (empty: generate one)") or given by `--admin-password-file`, and kept the same way. CUBE makes the `chris` superuser itself after each migration from `CHRIS_SUPERUSER_PASSWORD`. A generated password is shown once; setting it where it is used (a GitHub secret) stays the operator's act.
| The compute resource | `--compute` names the pfcon's resource (default: the VM's name), registered through `POST /chris-admin/api/v1/computeresources/`; the deploy then checks that `/api/v1/` shows `chris` the `admin` link, the test `FNNDSC/upload-chris-plugin` makes first. The store's is `NERC` because every plugin workflow uploads with `compute_names: NERC`.
| Name and certificate | Every public VM has a reserved address, so a rebuild never moves DNS. `chris deploy --host` writes the A record when the zone is in the tenancy. When it is not, it prints the registrar's instructions, naming the registrar from the zone's name servers and the record to remove (`cube.chrisproject.org` is a CNAME to NERC's router at GoDaddy), then asks public resolvers each minute for up to an hour; seen, Caddy obtains the certificate and the deploy checks `https://<host>/api/v1/`; unseen, it stops at "waiting on DNS" and a replay resumes there.
| What the store holds | The script ends at a working, empty store. Its first contents come from rerunning plugin upload jobs, the path every plugin uses. A backfill from another CUBE is ChRIS work, a verb of the ChRIS session (`plugin add --from <cube>`), not the substrate's.
| Backups | `--data-backup daily` is the cloud's native volume backup (OCI: a policy, daily, seven kept, incremental); `vm restore <name> --from <date>` swaps in a volume made from one. A database dump to a bucket needs a credential on the VM and is its own design.
| Teardown | A VM is born protected (`vm protect <name> off`). `vm teardown <name>` removes the instance and its boot disk and keeps the data volume, its backups and the reserved address, so replaying the script brings the store back with its data and name; the plan shows what is kept and what it costs. `--all` takes those too, asking for the name typed back. `net teardown` refuses while anything stands on the network, kept volumes included, and lists them.
| As code underneath | One Resource Manager stack per lifetime, from Terraform modules inside the OCI driver, never seen in a script: the network's (compartment, VCN, subnet, gateway, route, security list, bastion); a VM's data (volume, backup policy, reserved address); a VM's machine (instance, boot disk, security group, attachment, address assignment). A default teardown is a destroy job on the machine stack, `--all` on both. Each carries `mise-service=<name>`, so a fresh mise bastion finds them, as <<found>> finds domains. The plan, the alteration refusal and the drift count are D6's.
|===

*ChRIS profiles.* A ChRIS on a VM is the all-in-one CUBE, from CUBE's own `docker-compose.yml` (6.11.0 has no pman; pfcon runs in-network beside it), never a half CUBE: it always has a compute. A profile is data, one file naming its services and its floor (vCPU, GiB, disk), so a new profile is a file, not code: `minimal` is CUBE, its workers, Postgres, dragonfly, nats and pfcon; `complete` adds Orthanc, pfdcm and oxidicom. Variants take suffixes (`complete-keycloak`, `complete-ldap`). `chris deploy` refuses a target below the profile's floor and says by how much. No profile carries the ChRIS UI: the UI is porter and ARGUS. On a cluster ChRIS goes on with the Helm chart and the OpenShift values as an overlay; to the ChRIS layer there are two kinds of target, a host with Docker and a Kubernetes.

*The VM pane* is a controller in trek's pattern, as <<controller>> is for clusters: SIZE with sliders scaled to what the cloud sells (vCPU in the family's steps, memory within its range per core, disk from its minimum), the cost per hour and per month loud in the header; NETWORK (the name, the zone and whether it is the tenancy's, the open ports); BUILD; TEARDOWN. Every control lowers to the script's lines. Verbs come first; the mockup is grilled while they are built, and the panes follow once the lines are real.

*Order:* the rename; `net`, tried in a scratch compartment; `vm` (`new`, `plan`, `build`, `shell`, `protect`, `teardown`, `restore`); `chris deploy --profile minimal` with the DNS wait; the store's script played for real, done when the upload jobs of pl-shexec, pl-freesurfer and pl-dymap pass against `cube.chrisproject.org`; the panes; then `blt.chrisproject.org` on `complete` with a 1 TiB data volume, the proof it repeats. == Security

* *The creator posture* (cloud API key, Red Hat account, cluster admin) lives only in a substrate daemon; the research posture only in a domain daemon (<<two-sessions>>).
* *Spending and host control stay per daemon and off by default:* the `tasks` tier for build steps, which change the cloud and bill, `shell` for `!`; the guard refusing a non-loopback bind with any tier on, unless `--expose-host-control` is given, applies unchanged.
* *Secrets never cross `/vfs`* (<<identity>>).

[[cautions]]
== Cautions

* *One cloud draws the abstraction.* The driver interface, the fake driver and the ratchet are the answer (<<one-backend-many-clouds>>); a second real driver is the test.
* *`Oracle-Tags` drift.* Until clean re-plans are solved, every re-plan of a built domain shows alterations; `domain plan` must say which are tag drift.
* *Duplicate display names* are common in OCI, and Azure subscriptions share names too; the suffix rule (<<tree>>) has to hold everywhere a path is resolved. AWS accounts are numbers: the alias when set, else the id.
* *Rate limits and size.* Resource Search and the Limits API throttle; listings cache and refresh in the background.
* *One region, one domain* is all `harbor-oci` has proved; the tree and prompt allow more, but the build is not claimed for more until it has been done.
* *Terraform is one implementation of a step, not the domain machine.* MultiCluster Engine can itself create clusters (Hive; a Cluster API provider for OCI exists), so a hub may one day lay a Trusted Domain's instances down instead of the bastion's Terraform. `infra-plan` and `infra-apply` stay steps whose implementation the driver owns (<<port>>); the spec, the tasks, the controller and the tree never name the tool.
* *The descriptor will move again.* It was drawn from ChRIS and checked by the null backend; stratus is the first real second backend, and the descriptor should change where stratus shows it is wrong, rather than stratus bending around it.

[[fleet]]
== Later: a fleet of Trusted Domains

Verified 2026-10-20. Red Hat's fleet tool is *Advanced Cluster Management for Kubernetes* (RHACM, support matrix at 2.16 with MultiCluster Engine 2.11; included in OpenShift Platform Plus), the product form of the upstream *Open Cluster Management* project. A *hub* cluster runs the management plane; each managed cluster runs an agent, the klusterlet, that connects outward to the hub, so clusters behind NAT or in private tenancies work. The fleet is Kubernetes objects on the hub: `ManagedCluster` (one per cluster), `ManagedClusterSet` (grouping by label), `Placement` and `PlacementDecision` (choose clusters by label, count or score), `ManifestWork` (push any resource to the chosen clusters), policies for compliance, and an application lifecycle above them. A cluster built through the Assisted Installer can be imported into a hub, and MultiCluster Engine carries the Assisted Installer service itself. Two Red Hat things that are not this: *OpenShift Cluster Manager* at console.redhat.com, where the Assisted Installer lives and every cluster built through it is listed, which holds subscriptions but manages no workload or policy; and *Red Hat Edge Manager* (flightctl), fleet management for edge devices, not clusters.

What follows for stratus, in order, none of it before several Trusted Domains exist:

* *No hub first.* console.redhat.com already knows every TD stratus builds, through the same service account the build uses. A fleet listing comes from that API, read-only: a `fleet` verb, or `/net/redhat/clusters/` as one more mount under `/net`.
* *A hub is a cluster someone runs.* A hub holding administrator rights over every TD cuts against an institution controlling its own; a hub per institution, managing that institution's TDs, fits. Which it is is governance before it is design.
* *With a hub, the Kubernetes driver points at it.* `ManagedCluster` rows are the fleet; `Placement` and `ManifestWork` are how one ChRIS chart version rolls to many TDs. The same driver, one more kubeconfig; the TD controller gains a FLEET view.
* *Posture holds.* The agent pulls from the cluster; the hub never needs a cloud credential, so the bastion split (<<bastion>>) stands.

Sources: https://www.redhat.com/en/technologies/management/advanced-cluster-management[RHACM], https://access.redhat.com/articles/7136928[RHACM 2.16 support matrix], https://github.com/open-cluster-management-io/api[open-cluster-management-io/api], https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/installation_overview/ocp-installation-overview[OpenShift installation overview].
