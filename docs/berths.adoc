== Abstract

A berth is one person's mise session, running in a container of its own behind a spoke's door, with the ChRIS data they anchored under `/anchors`, their results at `/outgoing`, and a shell that is never on the machine that runs CUBE. This document owns the word, the topology and the decisions that build it. The spoke it sits in is <<dev-bastion.adoc#,dev-bastion.adoc>>'s subject; the host that runs the door is <<bastion.adoc#,bastion.adoc>>'s; how a spoke is built is <<stratus.adoc#,stratus.adoc>>'s.

[[words]]
== The words

CUBE is a server: its API hands out files, feeds and runs, and never a shell. The mise stack (calypso, chell, ARGUS) is a client of that API, and the shell it shows, `ls`, `cd`, `id`, `!`, is built inside the client; nothing on CUBE's side executes a command for a person. A client has to run on a computer: a tablet with chell on it, pangea, or a container that behaves as one. porter is a host for many people's clients at one door, as a jump host holds many ssh sessions. A *berth* is one person's client under porter, in its own walls: calypso, chell, the tooling, the two mounts and a home that persists. The *berth image*, `mise-berth`, is what a berth is made from; a berth is that image running, a container on a VM today and a pod on a cluster later. The word is the harbor's: a ship ties up at a berth, and the porter shows a person to theirs. It is not a bastion: that word already names the host that runs porter (<<bastion.adoc#host,bastion.adoc>>) and the cloud's own maintenance door (`vm shell`), and a third meaning would leave none of them sayable.

Three things, not one. The *image* is the read-only template, the same for everyone: the tools, calypso and chell, nothing of anyone's own. The *home* is a volume, a persistent directory that is one person's alone, `~/` with their dotfiles, `src/` and whatever they installed; it outlives any container. A *berth* is a running container: the image started with that person's home mounted at `/home/<user>`, plus `/anchors` and `/outgoing`. Stop the berth and the container is gone; the home stays. Start again, same image, same home, and the person is back where they were. So there is one home and one berth per person. What changes under a berth is its *anchors*: the paths in ChRIS whose data stands under `/anchors`, as mounts stand in a shell, and from which the place of the results follows. Adding or dropping an anchor never touches the home.

`!` in that chell opens a shell in the berth, as that person, in their home: the chell is already running inside the container, so the shell is on the same machine it is. On a porter without berths the same keystroke lands on the host porter runs on, as porter's own user, which is what the berth exists to replace.

A berth is a development environment only by what it is stocked with. The image carries a developer's tools today; another image could stock an analyst's. The berth is the place, not the stocking.

          +----------------+    |    +----------------+

   |  berth ana   |      | berth benito |      | berth rudolph|
   |  calypso     |      |  calypso     |      |  calypso     |
   |  chell  !    |      |  chell  !    |      |  chell  !    |
   |  /anchors    |      |  /anchors    |      |  /anchors    |
   |  /outgoing   |      |  /outgoing   |      |  /outgoing   |
   +------+-------+      +------+-------+      +------+-------+
          |                     |                     |
          +---------------------+---------------------+
                                |  cube-net (API only; berth-to-berth blocked)
                                v
                      +-------------------+
                      |       CUBE        |  + postgres, pfcon, caddy ...
                      +-------------------+
----

A hub and spokes. porter is the hub; each berth hangs off it on a wire of its own, `net-<user>`, a network whose only two members are porter and that berth. Every berth also stands on `cube-net`, where CUBE's API is, because the berth's calypso is the person's ChRIS session: the download of an anchor into `/anchors`, `gather`, `ls` and the upload at a close are all calls to CUBE made from inside the berth. `cube-net` blocks traffic between its containers, so a berth reaches CUBE and nothing else on it; porter is not on `cube-net`, so the block never stands between porter and a berth. No berth has a path to another: its own wire has no other berth on it, and `cube-net` forbids the hop. The launcher, which makes these wires, is not drawn; it stands beside porter and is the only process given the engine's socket.

This replaces the first build's one shared berth network, which kept berths apart with the same blanket rule and so also kept apart a porter that ran as a container on it; on pangea porter ran on the host, outside the network, and the rule never touched it.

[[files]]
== A person's own files

The lowest impedance for a person's own files is chell on the metal, on the machine where the files are: `upload` reads the local disk and talks to CUBE directly, and what comes down lands where it can be used. A berth's shell sees only its home and its volumes; a file from a laptop reaches it by an extra hop through the browser, and that hop is for a few files, never a dataset. So the two paths split by what the files are: a person's own data and results go through chell on the metal, straight to CUBE; cohort work goes through the berth, whose data arrives from ChRIS (`berth anchor`) and leaves through ChRIS (`berth close`), and never needs a laptop's disk.

[[settled]]
== What is settled

* *The VM plays the cluster.* Its containers play the pods: CUBE, its database, its workers, pfcon and Caddy on one side, the berths on the other. The VM itself is a node. No person works on it; the operator reaches it for maintenance over the cloud's own bastion service, which is a door for the operator and never for users.
* *porter is the spoke's door, one per spoke.* It signs a person in and starts their berth, as it starts a calypso per identity on any host.
* *Each person's berth is a container.* calypso, chell and the tooling run in it; `/anchors` holds what they anchored, which the session leaves without write permission, and `/outgoing` is their own. `!` under the `tasks` tier opens the shell of this container, so a person's shell is never on the machine that runs CUBE: it cannot reach the database, `cube.env`, the data volume or Docker. One person cannot see another's work or processes, and inside a berth there is one Linux user, so no mapping between ChRIS accounts and Linux accounts is needed.
* *A berth launcher holds the right to start containers, and nothing else does.* It runs beside porter and is the only holder of Docker's socket; porter asks it one thing, start or stop the berth for an identity. The launcher fixes everything else: the image, the person's volume, the mounts, the uid and gid (CUBE's own for that person), the limits, the networks, and no Docker inside. In a Trusted Domain it is a controller whose namespaced role can create berth pods and nothing more.
* *The berth is one image, `mise-berth`, built by CI and run by its tag `latest`.* It holds Node with the calypso and chell latest published on npm when it was built; on Debian trixie; Python 3.13 with uv and pip, and numpy, scipy, pandas, matplotlib, scikit-image, scikit-learn, nibabel, pydicom, SimpleITK, nilearn, chris_plugin, IPython and JupyterLab, with `python3.12` and `python3.14` beside it for a venv of the person's own; bash and zsh, tmux and manual pages; gcc, make, just, cmake, git with git-lfs, GitHub's `gh`, curl and the OpenSSH client; ripgrep, fd, fzf, jq and their like; starship, atuin, broot and lsd for a prompt of the person's own, and fortune; dcmtk and dcm2niix; the latest upstream Neovim, emacs-nox, vim and nano. It holds no Docker, no cloud CLI and no key, and runs as a non-root user with the person's CUBE uid and gid. What a person installs beyond it lives in their persistent home. The image and the script that reads its versions at each build are in `images/mise-berth`; it is published at `ghcr.io/harbor-medical-ai/mise-berth`, public.

* *Nothing is pinned: a deployment runs the latest porter, and a berth is made from the latest image.* `chris deploy --porter` installs `@fnndsc/porter@latest` from npm into an image it builds without Docker's layer cache, so every deploy takes the release npm names at that moment, with the calypso, chell and ARGUS it brings, and restarts porter; the version installed is read back from the image and kept in the deploy's record. The berth image is run as `ghcr.io/harbor-medical-ai/mise-berth:latest`, a tag the Berth image workflow moves at every build on main, and each build installs the calypso and chell npm names as latest. `make deploy` starts that workflow on main once npm serves the new versions, waits for it, and stops before any host is upgraded if it fails. The launcher pulls the image before it makes a berth from it, and a `chris deploy` pulls it too, so a moved tag is followed with no redeploy; a pull that fails is said in the launcher's log and the berth is made from the copy the host holds. A berth already running keeps the image it was made from until it is made again. The accepted catch: a berth and its porter can differ for the minutes between a publish and the image build finishing, since a porter installed in that window starts berths from the image of the release before. Nothing refuses that; the next berth made after the build is from the new image.
* *The person's identity is their CUBE token, and only that.* porter hands it to the launcher, which writes it to a tmpfs at `/run/mise/token` readable by the person's uid alone and rewrites it when it is refreshed; it is never on a disk, in the environment or in the image. No password enters the berth.
* *What a berth works on is its anchors, paths in ChRIS the person names from inside it* (decided 2026-11-13, with the operator; it replaces one plugin instance per berth, and before that a feed picked at the door). `berth anchor <path> [name]` is a mount in the shell's sense: it takes any path the person can read (a node, a folder or a file inside a node's output, an upload, a PACS series), downloads it through the CUBE API with the person's token, and leaves it at `/anchors/<name>/`. Several anchors stand in one berth at once. The name is the path's last part unless one is given, and two paths that end alike need a name. A berth starts with no anchor. Naming paths needs no screen at the door and no restart, and the download reads only what ChRIS lets that person read.
* *An anchor under the person's own feeds has a node; any other has none.* The test is the path alone. Under `/home/<user>/feeds/` the plugin instance the path runs through is the anchor's node. Anywhere else (uploads, PACS, `/PUBLIC`, `/SHARED`, another person's home) there is none, whatever feed the data sits in, so work on a feed someone shared is returned into a feed of the person's own and no check of who may write a feed is made.
* *A path inside a node anchors part of it.* `berth anchor …/pl-fshack_41/data/sub-01` downloads `sub-01` alone, and its node is `pl-fshack_41`: the berth is taken to have been shown the node's output and to have used that part, as a plugin that reads one subject does. Another subject is another close, a sibling node.
* *A node in flight is not anchored.* CUBE's status for the instance is read at the anchor, and anything but `finishedSuccessfully` is refused with the status: its output is incomplete and may change under the work.
* *The size is said before the download.* The files, the bytes and the room the host has. Above 10 GB the anchor asks first (`--yes` answers for a script), and one that does not fit is refused with the advice to anchor a folder inside it. `--refresh` downloads an anchor again.
* *Anchors are protected softly.* The session removes write permission from the files it downloaded: that stops an accident, not an intent, and suits the open posture. It keeps a list of what it downloaded, names and sizes, for the close. Checksums in that list, and a mount the person cannot write, wait for the sealed posture and its gate.
* *A berth has one `/outgoing`, and `berth close` returns it as one node, with no plugin of its own.* Work is made from its anchors together, data from a node and weights from an upload, so there is one result. The close writes `berth.json` into `/outgoing` (who, every anchor with its path and what was downloaded, the berth session, the source commit, the image, the time, where the node went), uploads `/outgoing` to the person's CUBE files at `/home/<user>/berth/<uuid>/`, and runs the registered ds plugin `pl-dsdircopy` on that folder, with a title that says it is berth work. `pl-dsdircopy` does nothing itself: its one parameter is of CUBE's `unextpath` type, which CUBE fills into the node's output after the run. So a berth session is a plugin instance run by hand, the person's time comes before the run and never inside it, and ChRIS's model, a container run to completion, is untouched. The provenance travels in the data, where a copy or a download keeps it, and not in a plugin's parameters, where CUBE could be asked for it; a `pl-berth` that records it as parameters is a later exchange of one plugin name. An empty `/outgoing` is refused: there is nothing to close.
* *Where the node goes follows from the anchors.* Every anchor under one node of the person's feeds: a child of that node. No anchor under their feeds: a new feed, whose root is `pl-dircopy`, the fs plugin ChRIS starts feeds from, over every anchored path, with the work its child; with no anchor at all the root is the work itself. Anchors of two nodes, or of a node and of paths with none: the close refuses, says why and names the two choices, `--infeed <anchor>`, a child of that anchor's node, and `--newfeed`. `--newfeed` is allowed in every case, and its tree holds every input; `--infeed` is the convenient one and leaves the other anchors to `berth.json`. `--name` names a new feed. A join node over several parents (`pl-topologicalcopy`) is the later answer for anchors of several nodes in one feed.
* *A close asks before it returns work still being written.* The session runs in the berth, where every process is the person's, so the close lists the ones still running beside its own, with the files they hold open under `/outgoing`, and asks; `--force` answers for a script. A half-written result returned as a finished node is the outcome it guards against, and a forgotten editor does not block a close.
* *A changed input is said, not refused.* A finished node does not change; a folder outside a feed can. The close compares what ChRIS holds with the list kept at the anchor, says what differs, writes it into `berth.json`, and goes on: the work is valid for what it read, and the record says what that was.
* *A close that cannot attach still saves.* When the node cannot be made, the upload stays in the person's CUBE files and the close says "uploaded, not attached" with CUBE's reason.
* *Nothing is removed by a close.* A close is often a checkpoint: the anchors and `/outgoing` stay, and a second close is a second node. `berth drop <name>` removes one anchor without a question, since ChRIS still holds it. `berth clear` removes every anchor and empties `/outgoing`, and asks first only when `/outgoing` holds files not yet closed. The uploaded folder in CUBE stays always, because on a ChRIS that stratus deploys it is the node's data: see the next point.
* *On a ChRIS that stratus deploys, the node holds a link, not a copy.* CUBE fills an `unextpath` folder in one of two ways, by deployment: with pfcon in-network and link storage (`STORAGE_ENV=fslink`, what stratus renders) the node's output is one link file, `home_<user>_berth_<uuid>.chrislink`, pointing at the uploaded folder; with plain filesystem storage it is a copy under a folder of that name. Run on a throwaway CUBE 6.11.0 from the store's compose on 2026-11-10: both `pl-dircopy` and `pl-dsdircopy` left the link and copied nothing, and removing the uploaded folder left the link dangling, the node no longer holding the data. Either way a plugin attached below finds the work one name down, not beside it. Accepted; a `pl-berth` that copies is the answer if it costs.
* *A feed's sharers reach its berth uploads.* Sharing a feed with write permission also opens the folders its links point at to the person it is shared with, so a shared feed's berth uploads can be changed by its sharers: the node's data is then only as fixed as that folder.
* *The verbs are subcommands of one word:* `berth` (the anchors with their paths, and when the berth last closed), `berth anchor <path> [name] [--refresh] [--yes]`, `berth close [--infeed <anchor> | --newfeed] [--name <feed>] [--title <text>] [--force]`, `berth drop <name>`, `berth clear`. Acts that exclude one another, each with options of its own, which is what subcommands state and flags on one verb would need rules for; it is the form `vm`, `chris` and `plugin` already have. On a host without berths `berth` says the session runs on the host and refuses the rest. Starting, stopping and removing a person's berth are the operator's acts and stay on the CHRIS.
* *The store is open.* The posture is the spoke's and is set on its CHRIS; sealed waits for the gate (<<dev-bastion.adoc#open,dev-bastion.adoc>>).
* *Limits are a policy of each ChRIS,* set among its CHRIS settings, with defaults read from the host's size. Capacity is the host's memory less the profile's floor's, divided by the memory per berth, on any host; a berth's CPU limit is a cap on CPUs it shares with CUBE, not a reservation, so it does not count, and a busy berth competes with CUBE for them; on a cluster it is a namespace ResourceQuota with limits per pod. A spoke that is full says so, "holds N, in use by …", and SPEC shows the capacity.
* *It stops at logout, or after two hours with no shell, no process and no surface;* a long run keeps it alive. A volume per person keeps the home and `src/`, and the anchors and `/outgoing` until they are dropped or cleared; the container is made from the image at each start, so a new image is in force at the next login. Removing a person's volume is an act of its own on their CHRIS row, asked first.

[[built]]
== The launcher and porter's switch, as built

The berth launcher is a second program of porter's package, `berth-launcher`: one version line, so porter and the launcher always speak the same API, while the right to start containers stays a property of the deployment (only the launcher's process is given the engine's socket). Its API is local (a unix socket of mode 0600, or loopback) and every call carries a secret both read from one file of mode 0600; it is exactly start, stop and status of the berth for an identity, a start naming the cohort (a feed's id) or none. The cohort is the berth's `cohort` label and its `MISE_COHORT`, and selects no volume; it stays in the API so a porter and a launcher of different releases still speak. A berth it starts runs the image, pulled first so a moved `latest` is followed, as the person's CUBE id (uid and gid alike), the token on a tmpfs at `/run/mise` of mode 0700 owned by that uid, written as that uid on stdin, the policy's CPU, memory and process limits, every capability dropped, no new privileges, no privilege, and a read-only root. A full spoke refuses with "this ChRIS holds N berths, in use by …".

A berth's container is named `<prefix>-<user>-<key>`: the user as the wire's name spells them, then the identity's key, which keeps apart two identities whose user names are spelled alike. A container named `<prefix>-<key>`, the name without the user, is the same person's berth: the launcher counts it as one, and removes it when it starts or stops that person's berth.

The wires are <<figure>>'s. Each berth's own wire, `<prefix>-net-<user>`, is a bridge the launcher makes as the berth starts and removes as it stops; porter's container is joined to it then and taken off it after (`BERTH_PORTER_CONTAINER`), and a porter on the host reaches the bridge as it is. `cube-net` is one bridge for every berth, made once, whose containers cannot reach one another; the CUBE API is reached on it at the address the spoke publishes it on, `cube-net`'s gateway on a VM where CUBE binds its port there, or the public name, so the URL resolves to the same address inside a berth as it does for porter, and a berth sees no other container on it. A launcher starting removes what an earlier run left: helper containers, and wires with no berth on them.

The volumes are the person's own, two of them, named by the identity's key. One home per person, `<prefix>-<key>-home`, mounted at `/home/<user>` for life. One work volume per person, `<prefix>-<key>-work`, holding `anchors/` and `outgoing/`, mounted by subpath at `/anchors` and `/outgoing`, both writable by the person's uid: the session downloads each anchor into `/anchors/<name>/` and takes write permission from what it downloaded itself (<<settled>>), so the mount is not read-only. The berth names the two places to its session in its environment, `MISE_BERTH_ANCHORS=/anchors` and `MISE_BERTH_OUTGOING=/outgoing`; a session without them is not in a berth. Both volumes carry the launcher's labels (`org.fnndsc.mise.berth`, `.identity`, `.user`, and `.volume`, `home` or `work`), are made at the person's first start, and are given to their uid and gid by a short-lived root helper that can change ownership and read past permissions and nothing else; a volume the helper did not give is removed again, so the next start makes and gives it anew. Each is mounted without copying the image's mount point over an empty volume, so that ownership stays. Every person has the one work volume whatever cohort porter names: a start naming another cohort makes the berth again on the same volumes, so its label is true. A person may also hold a cohort volume, `<prefix>-<key>-cohort-none`, from a launcher that mounted `/incoming` read-only and `/outgoing` from it by subpath. It is never removed. When the work volume is made the helper mounts that volume read-only and copies its `outgoing/` into the work volume's, once, symbolic links as links, and gives the copy to the uid; a copy that fails removes the work volume, so the next start copies again. A berth found running whose `/anchors` and `/outgoing` are not both the work volume's, as the engine's inspect names its mounts, is made again rather than handed back, the home untouched.

A porter starts berths only when its deployment sets `PORTER_BERTHS=launcher`; it then reads the person's CUBE id with their token at login, asks for their berth with no cohort, hands a later login's token to a berth already up, and stops the berth at logout. A berth's versions are its image's, never a reason for porter to restart it. A stratus session is not offered on such a door. The image is one constant in porter, `BERTH_IMAGE_DEFAULT`, the tag `latest`; the workflow also builds any pushed branch that changes the image as `sha-<commit>`, which a launcher runs when given it as `BERTH_IMAGE`.

On a ChRIS that stratus deploys, `chris deploy --porter` puts the launcher up beside porter unless `--berths off`: a compose service from porter's own image, the one service given the engine's socket (through the group that owns it), on no network, answering porter on a unix socket in `berth/run/` beside `berth/launcher.secret` (mode 0600, the image's `node` user's) and `berth/policy.json`, all on the data volume. porter runs as a container there, so the launcher joins it to each berth's wire. The deploy builds porter's image from the latest release on npm, reads from it the berth image porter names, pulls it (a tag, so every deploy pulls), and waits for the launcher's health. Each berth reaches CUBE by its public name: the launcher gives every berth that name at `cube-net`'s gateway (`BERTH_CUBE_HOST`), where Caddy's ports are published, so the session's URL is the one porter's is. The hop crosses the bridge's isolation from the gateway to the published ports; it is walked on Docker 29, on pangea and on the store. Turning berths off removes the berths and their wires and keeps every home. The limits per berth are CHRIS settings rows, BERTH CPU and BERTH MEMORY beside BERTHS (`--berth-cpus`, `--berth-memory`, one CPU and 2 GiB when unset); the deploy writes them to `policy.json` and restarts the launcher when the `policy.json` already on the machine differs from them and the launcher was running, and the CHRIS and SPEC bands say how many berths the machine holds at them. The launcher counts the host's memory in whole GiB, rounded up, because the engine reports what the kernel leaves after its own reserve (about 7.7 GiB of an 8 GiB machine), and every surface counts the machine at its nominal size. A deploy refuses a berth memory that leaves no berth above the profile's floor, and a `--berth-cpus` above the machine's vCPUs.

The operator reads every person's berth from porter at `GET /berths`, over HTTPS and through the door's own address, so no SSH session is made. It is asked with `Authorization: Token <CUBE token>` or with HTTP Basic credentials, the admin's as stratus holds them for the ChRIS it deployed. porter verifies the caller with CUBE itself and holds no list of administrators: it hands the header as it came to CUBE's API root, which answers a caller it accepts with its links and names the `admin` link to an administrator alone, the same link the plugin upload workflow reads (<<howto-store-vm.adoc#,howto-store-vm.adoc>>). No credentials, or ones CUBE refuses, is a 401; a CUBE user who is not an administrator is a 403; CUBE not answering, or answering with a redirect (never followed, so the header goes nowhere else), or the launcher not answering within 10 s, is a 502; the credentials are never logged or echoed. CUBE is asked at its API root with `?limit=1`, which is a list of feeds and so is kept to one item, the `admin` link being the same whatever the limit. Because an unauthenticated caller could otherwise make porter ask CUBE without end (a Basic header makes CUBE hash a password each time), a client address is allowed ten asks a minute, and past that is answered 429 with a `Retry-After` and CUBE is not asked; and CUBE's verdict on one header (administrator, not, or refused, never the credentials, kept under the header's sha256) is remembered for 30 s, so a surface that polls asks CUBE once in that time. The answer is `{at, berths: [{user, state, cohort, cpuPercent, memoryBytes, memoryLimitBytes}]}`: `running` is a berth container up, with one sample of the engine's stats (CPU as a percent of one CPU, memory in use less the page cache, and the berth's limit); `stopped` is a person with no container up and a home volume (labelled `org.fnndsc.mise.berth.volume=home`); a person with neither is absent, and the surface says none. Berths are matched by identity (user and CUBE) and not by user alone: a container's `org.fnndsc.mise.berth.identity` label and a home volume's (made with the label from now on) must be this porter's CUBE for the user, so a berth or home left by an earlier CUBE URL is not shown as this person's; a home made before volumes carried the label counts for its user. Of two running containers of one identity the first by name is reported. A berth the engine does not sample within 3 s is running with its usage unread. Memory is read as `docker stats` reads it: the usage less the inactive file pages (`total_inactive_file` on cgroup v1, `inactive_file` on v2), and the whole usage when that cache is as large as the usage. The read goes through the launcher's local API (`GET /berths/access?cubeUrl=…`, behind the same secret), because the launcher is the only holder of the engine's socket and porter never touches it. A porter that starts no berths answers `{berths: null, why: "this porter starts no berths"}`, which is an answer and not a failed read. stratus reads it with the admin's credentials beside the accounts (`chris status` carries it as the live read's `berths`, `berthsOff` for a porter that starts none, or `berthsWhy` when it could not be read: an older porter answers 404 and the reason names its version), and ARGUS shows it as the HOST ACCESS column of ITS USERS: `running · 3% · 210 MiB / 2 GiB`, `stopped · home kept`, `none`, and a dash, with `berths are off` under the listing for a porter that starts none and the reason for berths that were not read. It shows what stands and offers nothing: starting a berth, stopping it and removing a person's home are not controls there yet.

Walked on pangea 2026-11-08 with two people at once, on the cohort volume's places: each berth on its own wire with a stand-in porter container joined, both on `cube-net`; neither berth could reach the other's calypso or container on any network; both reached CUBE; the stand-in and a porter on the host reached both berths; `/incoming` read-only and `/outgoing` the person's own; a start with a cohort made the berth again on that cohort's pair with the home kept; a logout removed the wire and took the stand-in off it, the volumes kept; a launcher started over strays removed them.

[[open]]
== Open

* *A refreshed token takes effect at the berth's next start,* not live; and a launcher restarted forgets the tokens it held, so the next start needs a fresh login.
* *The two-hour idle stop* is not built; stop at logout is.
* *A short-lived root helper* gives new volumes to the person's uid at the first start; it is the one moment of root on the path.
* *A berth node's data is a folder in the person's CUBE files,* reached by a link: removable by its owner and writable by a feed's sharers. Whether the close should end with a real copy, by a `pl-berth` or by CUBE, is open. How a plugin below a link node sees it in its own `/incoming` was not run.
* *A berth's disk is not limited.* Homes, anchors and `/outgoing` are volumes on the data disk with no quota each; a person can fill it for everyone.
