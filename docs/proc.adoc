= /proc: CUBE's runtime state as paths
:toc:

`/proc` holds what CUBE has run, beside `/bin`, which holds what it can run. On Linux, `/bin/grep` is a program and `/proc/<pid>/` is one running process; here `/bin/pl-dircopy` is a plugin (`/bin/zip_v20240311` a pipeline, a script of plugins) and `/proc/jobs/feed_N/...` is one run of it.

[cols="1,1"]
|===
| Linux | mise / CUBE

| `/bin/grep`: a program | `/bin/<plugin>`, `/bin/<pipeline>`
| a process: one run of a program | a job (plugin instance) in `/proc/jobs/feed_N/<plugin>_<id>`
| a shell script's run: processes that belong together | a pipeline's run: CUBE calls it a *workflow*
|===

== /proc/jobs

Every feed this identity can see, and under each its jobs as a tree (a job's children beneath it), with `status`, `title`, `note`, `params`, `log` and the `data` link into the feed's files. The roster and the topology are cached and kept current by visits (a visit is a delta, not a re-walk); see the salsa `/proc` provider.

=== Finding runs

`find` answers `/proc/jobs` whole from the session's job index, so a question about runs asks CUBE nothing: `-plugin` and `-status` test what a job ran and how it ended, `-pipeline` and `-workflow` which pipeline run made it (`-pipeline ''` is a direct run), beside `-name`, `-type`, `-newermt` and the depth bounds. A feed whose jobs are not indexed yet is walked as `ls` would walk it. `-workflow N` asked by id reads the run's feeds alone: CUBE names the feeds its jobs are in, and only those are read, indexed or not, so a fresh session answers in those feeds' time.

The index keeps each job's `pipeline_name` and `workflow_id` from its CUBE row. Jobs restored from a checkpoint written before it kept them are read again once, feed by feed, behind the prompt; until a job's row is read, `-pipeline` and `-workflow` cannot judge it, and `find` says on stderr how many it left out (`find: N jobs not judged: ...`) rather than cutting them silently.

[source]
----
find /proc/jobs -plugin pl-dylld -status finishedWithError     # every failed pl-dylld run
find /proc/jobs -plugin 'pl-dcm*' -newermt 2026-10-10          # recent conversions
find /proc/jobs -maxdepth 1 -status started                    # feeds still running
find /proc/jobs -pipeline 'FreeSurfer*' -status finishedWithError  # failed FreeSurfer pipeline jobs
find /proc/jobs -plugin pl-dylld -pipeline ''                  # pl-dylld run directly, not from a pipeline
find /proc/jobs -workflow 1365                                 # every job of one pipeline run
----

On ekanite, a `find` over all 5,542 plugin jobs in 661 feeds answers in under a quarter of a second with no CUBE request. It sees what this identity sees: its own feeds, and those shared with it or public.

== /proc/tags

Tags as directories: `mkdir` makes one, `rmdir` removes one no feed wears, `setfattr -n tag` hangs one on a feed (`docs/menu.adoc`, Tags).

== /proc/workflows (removed)

`/proc/workflows/<id>/` projected one CUBE workflow: `title`, a `pipeline` link into `/bin`, and `jobs/` linking into `/proc/jobs`. It was deprecated and unmounted on 2026-10-17: it held no fact the jobs do not already carry, it was unbounded, and nothing consumed it. This section keeps why it was built and what was learned, so the reasoning is not lost.

=== Why it was built

A browser can save one file, not a folder. DOWNLOAD on a folder in ARGUS therefore asks CUBE to archive it first, as the ChRIS web UI's download does: it runs the registered pipeline `zip v20240311` (`pl-dircopy` then zip) and hands the browser the one zip (#234). Running a pipeline creates a workflow (and a feed and its jobs), and there was no way to see those runs: the archive left an unexplained feed in `/proc/jobs`. `/proc/workflows` was added so the run that a download started could be seen as such: which pipeline ran, and its jobs (#235, 2026-08-27; designed in `docs/menu.adoc`, Workflows). A collaborator's own workaround for a large file, running a zip plugin on his feed by hand, is the same mechanism.

=== What was measured (ekanite, 2026-10-17)

* CUBE holds 51,294 workflows and the count grows daily; 18,913 belong to one user's automated PACS, anonymization and neuro-tree runs, 21 to `rudolphpienaar`, none to the e2e identity.
* Listing `/proc/workflows` paged through all of them (about 512 pages at about 1.5 s each, some 13 minutes) on the session's lane, freezing every other command for that time; reading one workflow's `title` or following its `pipeline` link walked them all too.
* Every job already records its run: a plugin instance carries `workflow_id`, `pipeline_id` and `pipeline_name` beside `feed_id` and `status`. A workflow adds only its title and per-status job counts.
* Visibility differs by resource. Jobs are scoped to the feeds an identity can see (owned, shared, public); workflows are not. The e2e identity sees every workflow on the CUBE, other users' titles included, and not one job inside them.

=== The questions, and where they are answered

The questions worth asking are about runs: which pipelines ran (FreeSurfer, anonymization), every run of a plugin, which of them failed this week. A tree keyed by run id answers none of them without walking it whole; a tree per key (by pipeline, by plugin, by owner: `/dev/disk/by-id` style) is a group-by built as directories, one cached index per key, and still cannot express a combined filter. Each is a query.

* *Everyone's runs* are CUBE queries, filtered and paged on CUBE's side, answered in about a second with exact counts:
** `workflows list --search pipeline_name:freesurfer`: pipeline runs, each row with its job counts.
** `plugininstances list --search plugin_name:pl-dylld,status:finishedWithError`: runs of a plugin, by status. As `radstar`, `pl-dylld` reads 763 runs (757 finished successfully, 6 with an error), 2025-04-18 to 2026-10-16, run directly rather than from a pipeline, so no workflow ever listed them.
* *This identity's own work* is `/proc/jobs`, cached: the jobs' `pipeline_name` and `workflow_id`, shown as a column or an attribute there, say which run a job came from; the listing-aware grep of #1101 filters them locally.

=== Defects found on the way

* `workflows search <term>` and `plugininstances search <term>`, the forms the help documents, fail: the rewrite to `list --search` keeps the term as the first argument, which is then read as an unknown subcommand. `list --search field:value,...` works.
* `workflow jobs <id>`, `run`, `rename` and `delete` are in the help and have no handler in the builtin.
* A search term must name CUBE's field (`plugin_name:`, `pipeline_name:`, `status:`); nothing says which fields a resource takes beyond `inspect`.

=== What replaces it

`find` over `/proc/jobs` answered from the cache (`-plugin`, `-status`, `-newermt`; see Finding runs), the run's identity on the job rows (`-pipeline`, `-workflow`), the CUBE searches above with their short forms repaired, and the listing-aware grep of #1101. The provider (`salsa/src/vfs/providers/workflows.ts`) was removed with the mount; `salsa/src/workflows/` stays, as the `workflows` command's.
