A chell attached to a session runs a host command, pipeline segment or editor only when the line it sent asked for it. Each `shell`, `pipe` and `edit` request now names the asking line (`lineId`, the surface's own id), and chell runs it only against what that line asked for, read before it was sent by the engine's own routing (`lineHostOperations_read` in brasa): a `!` line its command, a later pipeline segment that is not a builtin exactly as typed, grep's and `command`'s delegated host lines, an `edit <file>` line one edit of that file as typed, and a `!` on the session's own pseudo-terminal the hand-over of this terminal (refused back to the session otherwise, which stops the program). Each grant is spent once and retired with the line, a cancel or the connection's close. A request with no line, for another line or connection, or for anything else runs nothing and says why. Lines chell cannot read that from (lists, captures, redirects, background lines, references or patterns the session expands) ask for nothing here. A delivered file must also come from a source the line named, matched against the root the session resolved (new `source` on `deliver`), each local place once. Pipeline routing follows the words the session lists at attach (`engineCommands`). The daemon refuses at its own side a host command or pipeline segment for a line another surface sent (a browser holding a terminal's line). What no grant covers is put to the person on chell's own terminal (`y`, `l` for the rest of the line, `r`, or `allow all` for the connection), with the session's output held while the question is open; with no terminal it is refused. `chell --remote --allow-host-requests` lets the session run anything it asks on this machine for that connection without asking. A session of an earlier release sends no line id, so its requests are offered only `y`, once, while one line runs.
